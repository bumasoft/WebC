13. The browser bridge

Reference · docs/reference.md

The C side emits a line protocol, the JS side replays it:

text
create <id> <parent> <tag>     #text for text nodes
attr <id> <name> <value...>
listen <id> <event>
text <id> <value...>
attrs-clear <id>
move <id> <parent> <before>    a reused keyed item that changed place in its list;
                               <before> is the anchor element id, 0 = end of parent
remove <id>

assets/webc.js exposes hydrate(root, commands), apply(commands), feed(chunk), start({wasm}), dispatch(name, event) (run a binding by name — a keyboard shortcut, a voice command, another script), diagnostics() and why(x, y).

A batch cannot half-apply. One malformed op — an attribute with no name, a create into a node that is gone — is skipped, counted, and named in the console; every other op in the batch still runs. Before that, a single bad line threw out of the replay loop and the rest of the page was simply never built, with no error to say so. WebC.diagnostics() returns { ops, badOps, lastBad, created, hydrated }:

js
WebC.diagnostics()   // → { ops: 1873, badOps: 0, lastBad: null, created: 10, hydrated: true }

Listeners are delegated. One real DOM listener per event type lives on the document and dispatches by node id, so an element that a patch re-creates keeps its binding, a click on a child reaches the element that asked for it, and portal() content still works. Node ids are stable for anything the framework reuses; names (data-hook) never move. Set globalThis.WEBC_DIRECT_LISTENERS = true before WebC.start() to attach one listener per element instead.

start({ data }) hands the module bytes. The seed JSON is copied into wasm memory as UTF-8 and the module is told the byte count — not text.length, which counts UTF-16 units. One accented letter in the seed makes those two numbers differ, and a JSON document that is merely truncated is not a crash: the parse fails, the app renders its empty state, and data: looks like it did nothing at all.

Hydration is verified. With hydrate: true the module's first batch adopts the server's markup node by node, by id. If a node cannot be adopted — a markup() slot, an id that moved between the halves — the elements the module did not claim are dropped instead of leaving both trees on the page, and WebC.diagnostics().hydrated is false.

js
WebC.diagnostics()
// { ops: 2250, badOps: 0, lastBad: null,
//   created: 1, createdEls: 0, anchors: 633, hydrated: true }

anchors is how many data-wc nodes the server sent, createdEls how many elements the first batch had to build (every text node is created on a perfect adoption, which is why the text count is separate), and hydrated is the verdict. The two halves have to render the same tree for adoption to work: seed the module from the server's own JSON with data: before it starts, and keep the first render free of anything that does not exist in the request (Date.now(), localStorage, a fetch that lands later).

"The click does nothing." WebC.why(x, y) names the element under that point and walks up its ancestors with the three facts that decide whether a click can reach it: display, pointer-events, and the node ids that actually have a listener.

text
[webc] why(420, 300) → span
  span #41 listens=NONE display=inline
  button #40 hook=pick listens=click display=block

13b. Running in a browser#

The same library compiles to wasm and runs against the real DOM. An app never tests for the target: it declares which files are server, shared and client in webc.json, and webc build compiles each set for the side it belongs to.

c
// src/app.h — the half both sides share
#include <webc/shared.h>
WEBC_MODEL(Todo, (id, i64, .pk = true), (title, Text), (done, bool))
Vec(Todo)
declare_view(Todos);
c
// src/view.c — markup only. It cannot reach a database or a request.
view(Todos, VecTodo *todos) {
  el("ul") { for_each(t, *todos) {
    el("li") { text("%s", t->title); el("button") { named("tick"); text("✓"); } }
  } }
}
c
// src/server.c
#include <webc/server.h>
#include "app.h"
GET("/")          { return page(Todos, db_all(Todo)); }
GET("/api/todos") { return json_list(200, db_all(Todo)); }
c
// src/client.c — signals, actions, the mount
#include <webc/web.h>
#include "app.h"
action(toggle, Todo *t) { t->done = !t->done; }  // no tick: the view re-runs (§11a)
client_main {
  mount(Todos, "#root");
  bind("tick", "click", toggle);
  return 0;
}

webc build produces both halves from those three sets; webc dev rebuilds both and reloads the tab.

Pieces:

PieceWhat it does
src/wasm_glue.cexports webc_start, webc_dispatch, webc_take_cmds, webc_cmds_len, webc_alloc, webc_free; calls the weak wc_app_main() (what client_main becomes) once from webc_start()
page(View, ctx)renders the view into the <div id="root"> of public/index.html, or into a bare fragment when there is no shell: the page the browser hydrates
named(name) / bind(name, event, action)the view names an element, the client names the behaviour; inside a keyed list the action receives the item
mw_web_assets(WC_WASM_PATH)serves /webc.js and /app.wasm with the right types and no-cache; WC_WASM_PATH is .webc/app.wasm, which is what webc build writes
assets/webc.jsinstantiates, fakes the WASI calls, attaches listeners, replays command batches

The shell loads it:

html
<div id="root"></div>
<script src="/webc.js"></script>
<script>
  WebC.start({ el: '#root', wasm: '/app.wasm', hydrate: true });
</script>

Serving it in production. A browser-only project has no server half, so webc serve is the server: a release build (-Oz), no watcher, no reload socket, and the framework's own chain over public/ and .webc/app.wasm with mw_compress() in front of it.

console
$ webc serve
  ▸ http://localhost:8080   (release, gzip on)

    module  app.wasm     151.4 KB    63.1 KB gz
    bridge  webc.js       64.8 KB    20.1 KB gz
    first load (gz)                  83.2 KB

What the browser actually reports for that page (transferSize, headers included):

ResourceOn the wireDecoded
/947 B647 Bunder the 1 KB floor, sent as it is, Vary still set
/style.css2.3 KB6.0 KB
/webc.js20.9 KB66.4 KB32%
/app.wasm64.9 KB155.0 KB42%
first load86.9 KB222.7 KB39%

A reload costs nothing: every one of them carries an ETag (the compressed one ends in -gz) and answers If-None-Match with a 304, so the second visit transfers headers only.

A project with a server half is built as a release binary and handed the process, so its own middleware decides; webc_use(mw_compress()) next to its mw_static is the same one line.

  • hydrate: true adopts the server markup by its data-wc anchors instead of building

    it again: the measured cost of the hand-over is zero created nodes.

  • A delegated binding resolves its item by key at click time, so a list that grows or

    shifts never hands an action a stale pointer.

  • A pointer event arrives with its position. The payload the bridge sends is the field's

    text for a field event and six numbers (\x01x,y,w,h,cx,cy) for a pointer event; ev_point reads the second (§12g). One payload field, two meanings, decided by the first byte.

Every callback owns an arena. An event, a timer, a fetch that settled, a field and a popstate all run outside a render, so there was no arena to reclaim what they allocate — and every synchronous js() copies its result into whatever arena is current. In a loop that is a leak with no reset point: one app's deep run made 21 million js("Date.now") calls, grew the app arena to 2 GiB, wrapped the command buffer's i32 pointer and froze the page with no error. Now each entry point from the bridge installs a callback arena, and two generations rotate: what a callback allocates stays valid through the next callback (so a render can still read a string it made) and is reclaimed two callbacks later. A callback that allocates more than 8 MB reports it once, by name, and starts from released chunks — js() in a loop is exactly that shape, and the message says so.

What a render costs, when a page feels slow and you need to know whether the render is the problem: WEBC_RENDER_COST=1 webc dev prints at most one line a second naming the worst render in it —

text
[webc] slowest render in the last second: #root — 3.41 ms

The measurement is two clock reads per render; the line appears only above 4 ms, and only when asked. Whole-view re-render is the model (§11a) and 2–4 ms is what it costs for a page-sized view; a render that takes 40 ms is a view doing work inside the render, and res_compute (§12b2) is where that work goes. A view whose changing value is a leaf can skip the render entirely — §12j.

13c. Calling JavaScript, and being called#

One door, typed where C can check it (<webc/js.h>) — examples/js is a page that walks through all of it:

c
str  title = js_str(js("document.title"), "untitled");                     // a property
js("localStorage.setItem", "theme", "dark");                               // two strings
i64  cores = js_i64(js("navigator.hardwareConcurrency"), 1);               // a number
bool online = js_bool(js("navigator.onLine"), true);
js("console.log", js_obj("{\"seam\":\"ok\"}"));                           // a JSON literal

Arguments are chosen from their C type by _Generic — a str or a literal is a string, an integer a number, a bool a boolean, js_obj("…") a JSON literal — so nothing in application source spells JSON, and a quote in a value stays a quote in a value. (A string literal reaches _Generic as char[N], undecayed; that is why the default branch is the C-string encoder.)

The result is a WJs, a value with a kind and its own error:

c
WJs r = js("no.such.thing");
if (!r.ok) log_warn("%.*s", (int)r.error.n, r.error.p);   // its failure, not a global
JVal *v = js_value(r);                    // the parsed value, or null

r.error belongs to that call, so three calls in a handler have three answers — js_error() was one slot for the whole module. A failure is also the one thing that is logged once, by the bridge, with the path in it.

A path is dotted from globalThis and may name a function (called with the arguments) or a property (read when there are no arguments). An object's fields are only readable when it serialises as data — JSON.stringify of a Response or a MediaQueryList is {}. There are no object handles in C, deliberately: a handle is a lifetime two sides have to agree about. When a call resolves with data, put the one line that unwraps it where JavaScript is written (window.api = { get: async (u) => (await fetch(u)).json() }).

Promises are callbacks, not an event loop and not await in C:

c
static void on_state(WJs r, void *ctx) {
  if (r.ok) set(state, js_str(r, ""));
}
js_then("fetch", "/api/state", on_state, nullptr);   // returns now

The handler runs when the promise settles, as an action: signals are written, the views re-render, the patch batch goes to the page. js_then returns false when there is no JavaScript or when WC_JS_PENDING_MAX calls are already in flight.

The other direction — the page driving the app:

c
webc_export_json(note) {                        // WebC.call('note', {text: 'hi'})
  JVal *v = js_value(in);       // the payload, already decoded
  set(stored, json_get(v, "text")->s);
}
action(bump) { set(calls, get(calls) + 1); }    // WebC.dispatch('bump')

WebC.call(name, …args) marshals the arguments, calls the export and flushes the patch batch; WebC.dispatch(name[, event]) fires the action a view named with named("bump"), with the context the listener was attached with. Both are for the click that does not come from the DOM — a keyboard shortcut, a voice command, another script.

The low-level form is still there and still the ABI: js_call(path, args_json) returns JSON text, and js_get_str/js_get_bool keep their defaults. On a server build every call answers "undefined" and js_available() is false, so one file can be both halves.

Toolchain: wasi-sdk (clang, wasm-ld and a sysroot). webc looks at WASI_SDK_PATH, ~/.local/share/wasi-sdk*, /opt/homebrew/opt/wasi-sdk, /opt/wasi-sdk, then wasm-ld on PATH; webc doctor reports which. Nothing else in the framework needs it.

text
make wasm                                   # examples/web → wasm
cd examples/web && ../../build/webc dev     # server + browser half, live reload

13d. The host: network, keys and the document — js() you never write#

js() is the escape hatch, not the tool. Everything an app actually does through it — fetch, POST, a stream, a timer, the address bar, the title, a focus — is a verb in <webc/host.h>, and the bridge is the only code that touches fetch, EventSource, history or document. A verb is a declaration: the C side says what should happen, an answer comes back as a call into the module, and nothing in an application ships a JavaScript shim to be the other half of the door. (The bug class this deletes is real: js("contrail.spin") once named a function that did not exist, returned ok: false, and the call site ignored it — a spinner that never spun shipped, and both halves compiled.)

c
#include <webc/host.h>

static void on_board(WJs r) { if (r.ok) board_read(r.json); }   // r.json: the body as text
static void on_link(WJs r) { /* {"state":"open"|"lost"} */ }

webc_get("/api/briefing/7", on_briefing);                        // one slot per call
webc_post("/api/flights/1/reroute", body, on_reply);             // body is JSON text
webc_subscribe("/api/stream", "tick", on_feed);                  // one EventSource per URL,
webc_subscribe("/api/stream", "state", on_link);                 //   however many hear it
webc_later(5200, on_toast_expire);                               // re-arms its own timer
res_get_json(res, fmt_s("/api/briefing/%lld", id), on_briefing); // a resource whose loader is a GET

The handler runs like an action: it writes signals, the batch that follows reaches the page by the same road a click takes. r.ok is false when the request failed and r.error carries the server's own words. A resource started with res_get_json walks the ordinary WRES_* states — res_state(r) != WRES_IDLE is "already asked" — and its handler owes the resource exactly one res_complete().

Typed fields and keys — one delegated listener each, in the bridge; the names and the behaviours live with everything else the app means:

c
el("input") { named_field("dest"); placeholder("LHR"); }      // the shared view
action(field_dest) { set(rdest, WC_AS_STR(keep(ev_value()))); } // the client half
bind_field("dest", field_dest);

on_key("meta+k", pal_open);      // one modifier plus one key; Mod+K fires anywhere
on_key("j", sel_next);           // a bare key never fires while someone is typing
on_key("escape", pal_close);     // escape is the one bare key that does

Modifiers are exact: shift+d does not fire on a plain d (and must not swallow it in a field), and alt is matched the same way. The document — applied after the batch's own mutations, so a title describes the tree that is now on the page and a focus() lands on a node that exists:

c
doc_attr("data-theme", str_lit("light"));   // an attribute on <html>
doc_title(fmt_s("%s — Contrail", f->number));
focus_hook("pal_q");                        // finds a data-hook, an id, or a data-field
reveal_hook("sel_row");                     // scrollIntoView({block:'nearest'})
field_value("draft", str_lit(""));          // a bound field's live value — a render cannot
                                            // write it back once the reader has typed
push_url(link_to(Flight, f));  replace_url(str_lit("/"));  self_path();
on_nav(navigate);  on_ready(ready);          // popstate; once, after the first batch

on_ready() is the moment a stream may open: the first batch is in the document, so the frame that follows has something to land on.

The live document, as one call — the pattern every streaming app repeats (two generation arenas, the stream pair, the seed hand-off, the link state):

c
static void board_read(str json);            // one callback: the seed and every frame
static void board_link(int state);           // optional: W_LIVE_* for the pill

WLive *board = res_live(&(WLiveCfg){
    .url = str_lit("/api/stream"), .event = str_lit("tick"),
    .doc = board_read, .state = board_link, .gen_bytes = 192 * 1024,
});
// wc_app_data(str json) { board_read(json); … }  // or res_live_read(board, json)
// action(ready)        { res_live_open(board); } // the subscribe pair

While doc runs, the next generation arena is current: decode into it with the model codec and persist() anything that must outlive the frame. The old generation dies only after the new one is live.

The page env on both halves — page_env() in the browser half is the same fact c->page.env is on the server (the bridge hands it over before client_main runs):

c
set(dark, page_env().dark ? 1 : 0);   // the edition the server rendered, from the cookie
str born = page_env().path;           // where the document was rendered (self_path() is "now")

Client routing's arrival is a match, not a string walk — on_nav actions receive a WNav: the path and the match against the same route table the server answered.

c
action(navigate, WNav *nav) {
  i64 id = 0;
  str num = nav_param(nav, "number");       // nav_param_i64 for a number
  if (nav->matched && num.n) { /* find the leg */ }
}

The components — #include <webc/ui.h> for the controls every console reaches for, ARIA threaded: switch_(hook, on, label), seg(hook, on, label, count?), tab(hook, on, label), meter(label, value, max, readout, cls), kbd(text), and classes("row", cond ? "sel" : NULL) for conditional class names without a format string. Opt-in include, markup only.

The browser half, tested without a browser — #include <webc/client_test.h>: CLIENT_TEST, client_dispatch("row", "click") (the view must have rendered once), client_press("meta+k"), client_type("dest", "LHR"), and EXPECT_SIGNAL(live, 1). The seams are the bridge's own tables, so anything the browser does through a verb, a test can do through a hook.

13e. The boot block: a project with no HTML file#

A fullstack project does not ship public/index.html. The document is generated from webc.json, so the mount point, the stylesheet, the title and — the part every project got wrong — the WebC.start() options cannot drift from the routes the server actually serves:

json
"boot": {
  "title": "Contrail — Vela Air global ops",
  "lang": "en",
  "css": ["/public/style.css"],
  "icon": "data:image/svg+xml,…",
  "el": "#root", "portal": "#portal",
  "data": "/api/board",
  "hydrate": true
}

page_auto() builds the shell from this block when no public/index.html exists (a project that ships one keeps it, and it wins). With "inline": true and a str webc_seed(Arena *) in the server half, the page embeds the document it was rendered against (<script type="application/json" id="webc-seed">) and the boot script reads it instead of fetching: no tick can land between the render and the seed, and the seed round trip disappears. Without webc_seed the fetch stays. The values are escaped on the way in — a title with a quote is a title, and a </script> in a URL cannot end the boot script. webc new --template=fullstack writes a boot block and no HTML file; wc_shell_auto() and wc_shell_has_boot() are the doors a test uses.

Every key, checked. webc.json is read against a table, so a key that is not here is an error that names the line and, within two edits, the key you meant — "clinet" is reported as did you mean "client"?, not as a build that quietly produced nothing. A key with the wrong type says what the key is for ("port" wants a number — the port webc dev serves on), and a source file listed in two file sets is refused: it would be compiled twice, once per half, and the linker would take whichever object it saw first.

Paths may be folders. A set holds paths, so "server": ["src/server/admin/editor.c", …] is as ordinary as "src/main.c". Nothing globs: the set is the answer, and a file nobody listed is not compiled into the wrong half by accident. Two things make folders comfortable — every compile line carries -I src, so #include "app.h" resolves from any depth, and each object keeps the shape of its source's path (src_views_admin_editor_c.o), so a posts.c in two folders is two objects, two symbols and two names in an error. What a move does change is #embed "…", which is relative to the file that writes it.

keytypewhat it is
namestringthe app's name, in logs and the page title
versionstringwebc version, the deploy manifest
descriptionstringone line for the manifest
entrystringthe server half's main source (default src/main.c)
webstringthe browser half's entry, for a project with no server binary

13f. webc.json: the 404 page and the policy#

The default for a URL nobody routed is 404 with a flat JSON error — right for an API, wrong for a browser. Two keys change only that case, and neither changes anything when it is absent:

json
"not_found": "public/404.html",
"csp": {"img_src": ["'self'", "data:", "https://cdn.example.com"]}

not_found is the page a browser gets: the file's markup inside the app's own shell, so the 404 carries the title, the theme and the nonce like every other page, with head_title("Not found") in the tab. §8c is the mechanics — what wins, what is left alone, and what a whole-document file does. A client that sent Accept: application/json still gets the JSON error, and a route that answered 404 with HTML keeps its own page.

csp is the policy as four parts instead of one header spliced by hand (§8a). A project that needs neither key writes neither key, which is why this is a section about two settings and not a page about configuring a framework.

13g. lint.exempt: when an app's history has to name the word#

webc lint --all reads the app's docs as well as its code, and a document that keeps an honest history — "we used parse_iso( here and it was wrong, and this is why" — names a retired spelling in order to forbid it. A grep cannot tell that from teaching it, so the gate fails on the one file that is being helpful, and the usual answer is to delete the history.

json
"lint": {"exempt": ["docs/history.md", "docs/appendix/"]}

A suffix match, so the entry may be relative, absolute or a directory. Up to sixteen, which is more than any app's history needs. The exemption applies to the docs half only: an exempt file is still compiled, still tested, and its code is still linted — what is skipped is the prose scan. A key that is not exempt is reported by the same unknown-key check as every other ("exemptt" → did you mean "exempt"?).

webc check ends with a wiring pass: named()/named_field() in the views reconciled against bind()/bind_field() in the client half, actions against the names that wire them (bind*, on_key, on_ready/on_nav — and on_click(act)/on(act, …) in a view, which is a wiring: the element carries the listener), on_key specs against the bridge's own grammar, and the classes the views emit against the selectors the stylesheets carry (both directions). These are the strings the compiler cannot check — the bugs of three real sessions were all wiring, and so is a note nobody reads: an app that wires every button with on_click would report every one of those actions as dead code. Notes for choices (a palette-only control, a state class), errors for the things that cannot work (a bind to a name no view declares, a key spec nothing would match). webc check --wiring runs just this pass, no build — the thing an editor runs on save.

Two shapes the pass had to learn, both of them ordinary in a growing app:

  • A hook name computed at runtime still wires its action. `for (i = 0; i <= n; i++)

    bind(tab_hook(i), "click", tab_pick)is the whole tab strip — one action, n names off a table. The pass reads the call's own closing paren (an argument's paren is not the end of the call), skips quoted arguments, and recordstab_pick` as reachable. It cannot name the hooks, so it says nothing about them; a test that dispatches every name in the table is the check for that half, and it is the better one — it runs the view.

  • A comment is not a wiring. These notes are reconciled from source text, so `//

    on_click(dead_code)in a prose line makes a dead action read as reachable, and a// see on_click(tab_flat)would emit a prototype for an action that does not exist. Lines are stripped to their code before the pass reads them (//to end of line,/* … */` skipped, both only outside string literals).
