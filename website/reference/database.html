Docs/Reference/9. Database

9. Database

Reference · docs/reference.md

Three drivers open from one URL — sqlite (a path), postgres, and MySQL/MariaDB (§9a5). Handles below are WDB *; the statements are the raw layer. The ORM is §9a to §9a4 and it is what an app should be written in: a typed filter, one row, a relation, a page, a tree of rows. Raw SQL is for the statement that is a report, not for the tenth select * where id = ?.

c
WDB *db = db_open("sqlite:data/app.db");      // or postgres://…, mysql://…
db_insert(db, Todo, &t);                       // INSERT with named params underneath
                                             // (returns bool; db_insert_into(db, T_modelof(), &t, &id)
                                             //  also reports the new key)
WRes r = db_exec(db, q("select * from todos where done = :d", .d = false));
i64 n = row_i64(&r.rows[0], "id");
str s = row_str(&r.rows[0], "title");

Lists come back in the order you ask for — db_all() has no opinion of its own, which made a front page look right on sqlite and wrong somewhere else:

c
VecStory *latest = db_all_ordered(db, Story, "published desc");
VecStory *top    = db_all_where(db, Story, "where views > ? order by views desc", qy);
  • :name placeholders are rewritten to ? (sqlite) or $n (postgres and MySQL); the same

    code runs on all three. The rewrite lexes: a colon inside a string literal, a quoted identifier or a comment is left alone, so to_char(now(), 'HH24:MI:SS') survives.

  • db_insert(db, T, &t, &id) reports the new key from every driver: sqlite from its rowid,

    postgres because the statement asks with returning, MySQL from the OK packet — which is the returning capability in §9a5, not three code paths in the app.

  • db_all(db, Model) returns Vec<Model> *.
  • A transaction belongs to a session, and a session to a request. The first statement a

    request makes pins one connection for that task; every later statement — and any transaction — runs on it, and the connection goes back to the pool when the request ends, even if the handler panicked. Two requests can therefore never sit inside each other's BEGIN/COMMIT: when they can, a rollback undoes another request's committed insert.

c
tx_scope(db) {                       // BEGIN on this request's own connection
  db_save(Order, &o);
  if (!charge(o.id)) tx_commit_here();   // …or let the scope roll back
}                                    // no commit → ROLLBACK

tx_scope(db) { ... tx_commit_here(); }

tx_scope(...) { … } takes a block. A nested scope is a SAVEPOINT, so an inner failure can roll back alone (tx_rollback_here()), and committing a scope that is not open is a failure with a message in WTx::err, not a silent false: a commit that quietly does not commit is how a write vanishes. tx_begin(db) / db_begin-style handles remain for code that must end a transaction in a different function than it started.

  • A task that ends inside a transaction has it rolled back and its connection returned (a

    warning names the task): fail() and a panic both unwind past the scope's cleanup.

  • Migrations: migrations_apply(&(WMigrate){ .db = db, .dir = "migrations" }), files

    applied in filename order, recorded in schema_migrations. A migration is SQL, so it carries the dialect of one database: postgres needs bigserial where sqlite wants integer primary key autoincrement. Put the other spelling next to it as 0001_todos.postgres.sql (or .sqlite.sql); it is used instead of 0001_todos.sql when present, and the same name is recorded, so one sequence of migrations serves every dialect — .sqlite.sql, .postgres.sql, .mysql.sql. examples/todo and examples/accounts carry all three spellings. A file may carry several statements: a query with no parameters goes out on the server's simple protocol, which is the one that takes them, so nothing about the file depends on the driver.

  • A migration's column type follows how the field is stored, not how it reads. An enum

    field (RPlan, RKind) is stored as its name — "balanced", "stake" — so its column is text, never integer; a bool is boolean (or tinyint(1) on MySQL). SQLite accepts a name in an integer column and will not tell you, which is how an app can have a postgres migration that has never once run: invalid input syntax for type integer: "balanced". Money stays integer cents, and an indexed text column is varchar(190) where MySQL needs a length.

  • The pool opens connections on demand, up to WC_DB_POOL (default: the number of

    processors, at most 256), and a task waiting for one parks rather than spinning the CPU. Waiting is FIFO and bounded: after db_pool_config(max, acquire_ms) milliseconds (WC_DB_ACQUIRE_MS, default 5000) the request is refused with a message that names the pool size instead of hanging until the client gives up. db_pool_size(db) reports what is open.

  • The postgres driver does not block a thread. Its socket I/O parks like every other

    fd in the runtime, so a slow query holds a connection, not a processor: 64 concurrent select pg_sleep(0.3) finish in one wave rather than in batches of nproc. A statement also stops when its request is cancelled — the session carries req->ctx, and the driver sends a protocol CancelRequest for the backend, so mw_timeout_ms() can answer 504 without waiting for a query it already gave up on. That connection is then closed and its slot recycled; a lost connection no longer poisons the pool.

  • TLS to postgres follows libpq: ?sslmode=disable|prefer|require|verify-ca|verify-full

    (default prefer, or WEBC_PG_SSLMODE), with sslrootcert= for the verify modes. A build without TLS refuses require at startup instead of sending a password in the clear; managed postgres, which rejects plaintext clients, is the reason this exists.

  • A null handle is a refusal, not a crash: db_insert_into(nullptr, …) and the model

    helpers return an error naming DATABASE_URL instead of dereferencing it.

9a. A filter you can read, and one row by one field#

Asking for one row by a field the long way round is a query built only to carry the value:

c
WQuery *qy = q("select 1");             // a statement with no meaning
q_str(qy, "s", slug);                   // whose only job is to hold `slug`
const Section *sec = db_find(Section, "slug = :s", qy);

Nothing checks the field name, nothing checks the operator, and you have to know who owns the query's arena. Three spellings replace it, one per shape of question.

One field, one value. The field is checked against the model — a typo panics and lists the fields that exist instead of returning no rows — and the value is always a bound parameter:

c
const Section *sec = db_by(Section, "slug", slug);
VecStory *mine     = db_all_by(Story, "section", str_lit("science"));
i64        n       = db_count_by(Story, "section", str_lit("science"));

The value may be a str, a const char * or an integer; a string literal goes through str_lit() (_Generic does not decay an array). Each takes a WDB * first when you are not using the default handle: db_by(db, Todo, "id", 3).

More than one condition. WWhere names the field in the macro, so the compiler checks it, and the primary key column comes from the model, not from a string:

c
WWhere w;
ww_init(&w, nullptr);
ww_eq_str(&w, Story, section, value);
ww_order(&w, Story, published_at, true);
ww_limit(&w, 2, 0);                     // the query cuts; the caller stops truncating

VecStory *list = db_all_w(db_default(), Story, &w);   // rows, ordered and limited
Story    *one  = db_one(db_default(), Story, &w);     // the first row, or null
i64       n    = db_count_w(db_default(), Story, &w); // how many, without reading them
ww_free(&w);

ww_or_begin() / ww_contains() / ww_or_end() make one question out of several columns instead of filtering the whole table in memory:

c
ww_or_begin(&w);
ww_contains(&w, Story, title, qtext);   // lower(col) like lower(:p) escape '!'
ww_contains(&w, Story, dek,   qtext);
ww_or_end(&w);

db_increment(Story, st, views) adds one to one column in one statement — the alternative, st->views += 1; db_save(Story, st);, rewrites the whole row (body and all) to change a counter.

Set WEBC_TRACE_DB=1 to log every statement with its row count and duration.

9a2. Relations: one declaration, one query, no query in the view#

A story has a section, and the section is a row. Declare it next to the models:

c
WEBC_MODEL_REF(Story, section, Section, slug)   // "Story.section holds a Section.slug"

Fetch the whole list once and link it:

c
VecStory *all = db_all_ordered(db_default(), Story, "published_at desc");
prefetch(all, Story, section);          // one extra query, for every row at once

Read it in the view, server or browser half, with no query at all:

c
const Section *sec = ref(Story, st, section);   // the row, or null if nobody prefetched

The links belong to the request (they live as long as its arena does), and prefetch is one select … where slug in (?, ?, ?) however long the page is. A relation nobody prefetched reads as null rather than issuing a query per row — the N+1 that is invisible until the page is slow. WEBC_MODEL_REF is pure data, so it belongs in the shared header with the models; only prefetch needs a database. prefetch_on(db, vec, T, field) is the same on a handle you own (a test).

Postgres speaks protocol v3 with SCRAM-SHA-256 authentication; there is no libpq. It is tested against a real server: make pg-test starts a throwaway postgres in docker, runs tests/db_parity_test.c (the same story through every driver it can reach, compared field by field) and both example suites against it, then removes the container. make mysql-test is the same for MySQL 8 (§9a5). Without docker but with a server, set WEBC_PG_URL. An app's own tests run on postgres with WEBC_TEST_DB=postgres://… webc test.

9a3. The other direction: a section's stories, still one query#

WEBC_MODEL_REF answers "what is this row's section" with one row. The reverse question has its own declaration, because it is a different question with a different result:

c
WEBC_MODEL_REF(Story, section, Section, slug)     // story  -> its section
WEBC_MODEL_MANY(Section, stories, Story, section) // section -> its stories

The second line names the same relation, read backwards, and generates a typed accessor — refs(Section, sec, stories) returns a VecStory *. Prefetch it for the page the way you prefetch the single direction:

c
VecSection *all = db_all_ordered(db_default(), Section, "name");
prefetch(all, Section, stories);            // ONE query, however many sections
for_each(sec, *all) {
  for_each_ptr(st, *refs(Section, sec, stories)) el("li") { text(st->title); }
}

That is one statement for the sections and one for all their stories — not one per section. A page of 2 000 sections chunks the owner keys in groups of 512, so the parameter count never runs into a server's ceiling. A collection nobody prefetched reads as empty, and logs relation read without a prefetch once, naming the model and the field: an empty list that was never fetched is the failure that looks like an empty section, and silence about it is how a page loses its rows.

Hops chain left to right — each one is a query on the rows the previous hop found:

c
prefetch(all, Section, stories, author);    // 2 statements: stories, then their authors

Three hops is the limit; deeper is a loop in the app, because a path string is a second query language nobody asked for.

9a4. Questions about a relation, a page, and a whole tree#

Filters reach through a relation without changing the shape of the result (so the rows still read back into models), sort by a related column, and aggregate:

c
WWhere w; ww_init(&w, nullptr);
ww_in_ref(&w, Story, section, (WWhere *)section_filter);   // section in (select …)
ww_order_ref(&w, Story, section, Section, name, false);    // order by the section's name
db_sum(db_default(), Story, views, &w);                    // also min, max, avg, count

An aggregate answers over the conditions: an order by and a limit in the same filter are dropped, because a sum of the first page is a different question and the wrong answer looks plausible.

A list that is not the whole table is three fields and two statements:

c
WPager pg = {.page = 2, .limit = 20};
VecStory *page = db_page(db_default(), Story, &w, &pg);
// pg.total, pg.pages, pg.has_prev, pg.has_next — a page past the end clamps to the last one

And a row that owns rows is written as one thing:

c
i64 n = db_save_all(db_default(), Order, &order, items, &n);  // FK filled from order.id
db_delete_tree(db_default(), Order, &order, items);            // children first

db_save_all takes the collection, not a field name: the WEBC_MODEL_MANY declaration is what says which column holds the parent's key, so there is exactly one place the relation is described. It joins an open transaction or opens its own, so a failure takes the whole tree with it.

9a5. The third dialect: MySQL and MariaDB#

mysql://user:pass@host:3306/db and mariadb://… open the same driver, which speaks the wire protocol directly — no libmysqlclient, no .so to install:

c
// DATABASE_URL=mysql://app:secret@127.0.0.1:3306/app
// ?ssl-mode=prefer|require|verify-ca|verify-full, ?ssl-ca=/etc/ca.pem

Authentication is mysql_native_password (SHA-1 scramble) and caching_sha2_password (the SHA-256 fast path, with full authentication only over TLS). sha256_password requires TLS; ed25519 and GSSAPI are refused by name with the two alternatives spelled out, rather than failing as a bad password. There is no RSA public-key exchange on purpose: a client that would hand its password to whatever key the server offers is a client that gives the password away to a man in the middle.

A statement with no parameters goes out as COM_QUERY and may carry a whole migration file; a statement with parameters is prepared (COM_STMT_PREPARE) and executed as binary rows, cached per connection. Sessions are set to STRICT_TRANS_TABLES, utf8mb4 and time_zone='+00:00', so a too-long value is an error (422) instead of a silent truncation, and a datetime means the same thing everywhere.

What differs is declared, not branched on: each driver is a table of four flags, and every statement above reads them instead of asking which server it is talking to.

flagsqlitepostgresmysqlwhat an app sees
returningnoyesnodb_insert reports the new key everywhere: last_insert_rowid() here, insert … returning there, the OK packet's last_insert_id on MySQL
offset_needs_limitnoyesnoww_limit(&w, 0, 40) becomes limit 9223372036854775807 offset 40; the largest signed value, because MySQL documents the unsigned one and sqlite answers datatype mismatch
ident_quote""`a model with a rank, groups or order field is quoted, so a reserved word is a column name and not a syntax error; a name that is not a plain identifier (public.users, a .sql() override) is passed through
multi_statementyesyesyesone call may carry a whole migration file

WC_DB_DRIVERS[] is that set as data ({"sqlite", "postgres", "mysql"}), which is what the migration runner reads when it looks for a <name>.mysql.sql twin. driver_for() refuses an unknown scheme:// at open, naming the URLs this build speaks. Opened as a sqlite file named after the URL, the first sign of the mistake is "my tables are empty" three screens later.

Driver errors carry a class (WDBE_CONFLICT, WDBE_BAD_REFERENCE, WDBE_NOT_NULL, WDBE_TOO_LONG, WDBE_CHECK, WDBE_DEADLOCK, WDBE_TIMEOUT, WDBE_AUTH, WDBE_LOST) mapped from the server's own codes, so a duplicate is 409 on every driver without searching an error message for the word "unique". On MySQL the codes are errno: 1062/1586/1451 conflict, 1452/1216/1217 bad reference, 1048/1364 not-null, 1406/1264/1292 too long, 3819/4025 check, 1213 deadlock, 1205/3024 timeout, 1045/1698 auth, 2006/2013/1053 lost. The class picks the status: 409 / 400 / 422 / 422 / 422 / 503 / 503 / 500 / 500. An error a driver cannot classify stays WDBE_NONE and answers 500 with the server's own sentence, deliberately — a guess at 409 is worse than a 500 that says what happened.

Two things are worth knowing because they are the same value in a different shape:

  • An aggregate is DECIMAL on MySQL, not the integer postgres returns. sum(int) arrives as

    DECIMAL(32,0) and is read back as an integer, avg(int) as a real — the digits decide, so db_sum/db_avg answer the same numbers on all three servers.

  • A like pattern is escaped with !, not with a backslash: a backslash is an escape

    character inside a string literal on MySQL, where escape '\' is a syntax error. The query builder writes escape '!', so a search box works on every dialect.

make mysql-test starts a throwaway MySQL 8 in docker, runs tests/db_parity_test.c across all three dialects, tests/db_mysql_test.c against the server, the ORM suites (they read WEBC_TEST_DB) and both example apps, then removes the container. It has run green on MySQL 8.4 and MariaDB 11.8. Without docker but with a server, set WEBC_MYSQL_URL; without either, every MySQL test skips with the reason in its name. An app's own suite runs against it with WEBC_TEST_DB=mysql://… webc test, and migrations may carry a <name>.mysql.sql twin next to <name>.postgres.sql — examples/todo and examples/accounts each have one, which is why their suites run on the third dialect too.

A request with a deadline gets its cap pushed down to the server too: the driver sets max_execution_time (MySQL) or max_statement_time (MariaDB) from the request's remaining time, and a statement still running when the handler gives up is killed with KILL QUERY <id> on a second connection — two halves of one promise, because the cap is per statement and the kill is now. A connection the server dropped (2006, 2013, 1053) is classed WDBE_LOST and retired instead of being handed to the next request.

The URL may also name a unix socket, for a container whose socket is not in a URL's authority section: mysql://user:pass@localhost/app?socket=/run/mysqld/mysqld.sock.

The container the target starts passes --mysql-native-password=ON, because that is the one auth plugin a non-TLS build can speak: MySQL 8.4 only loads it on request, and root otherwise authenticates with caching_sha2_password, whose full path wants TLS. The TLS half of the driver is checked from a TLS build, which keeps its binaries in build/tests/:

bash
make WEBC_TLS=openssl test
WEBC_MYSQL_URL="mysql://root:webc@127.0.0.1:3306/app?ssl-mode=require" \
  ./build/tests/db_mysql_test

9b. Fixtures and schema drift#

Two things every model-first project needs and neither of which needs a generator: put some rows in a table, and find out when the models and the tables have drifted apart. Both run inside the application binary, because that is the only process that has the models.

c
// src/boot.c — a demo or a test loads content/<table>.json (an array of objects)
void webc_boot(void) { seed_all("content", false); }   // false: only when the table is empty
bash
webc seed            # run the app's boot, then load content/<table>.json for every model
webc seed --reset    # ... deleting the rows first
webc check           # build, test, doctor, boot, schema, routes, consistency
webc check --verbose # ... and every finding, with the one-line fix

The last line of webc check is the consistency pass: the mechanical questions a reviewer asks, each one a grep with a rule narrow enough not to lie.

text
  consistent    2 notes (0 errors) — webc check --verbose lists them
  note ./src/server.c:63
    a query built only to carry a bound value
    fix: db_by(Model, "field", value) — one field, one value, no carrier
what it looks forseverity
q("select 1") — a carrier query (§9a)note
fmt("/a/%s", …) where a model already names /a/:slugnote
a month or weekday table, / 220 for a reading time (§4b)note
bind("x") with no named("x") — a click that can never fireerror
a file that renders pages and sets no titlenote

Comments are skipped: prose that mentions an idiom is documentation, not a use of it. Notes do not fail the check; only an error does.

seed_from_json(Model, "content/stories.json") is the single-table form and returns the rows inserted; a second call on a non-empty table inserts nothing, so a seed in webc_boot does not double the site. Rows are parsed and validated by the model, so a fixture that would fail an HTTP request fails the seed and says which field.

Schema drift is the failure this prevents: a model with a column the table does not have surfaced as a 500 on the first read of that column. webc_schema_report(db, out) compares every registered model (every WEBC_MODEL registers itself) with select * from <table> where 1 = 0 — the column names, every driver, no pragma — and prints what is missing and the statement that fixes it:

text
  schema         sqlite, 3 models
  Story          .views            missing from "stories"   → alter table stories add column views INTEGER;
  Story          table "stories" is missing      → run your migrations, or: create table …
  schema         DRIFT: 1 table(s), 1 column(s) missing

webc check runs it; a model marked WEBC_MODEL_INTERNAL (the framework's own RowId) owns no table and is skipped — and WEBC_ROW is that same macro with a name that says why (§4).

9b2. The migration the models imply: webc migrate diff#

The report above ends with the fix, and the tool can write it. webc migrate diff runs the app (the only process that has the models, exactly like the schema check), turns the same comparison into statements, and prints them:

bash
webc migrate diff                 # what is missing, as SQL, on the terminal
webc migrate diff --write         # migrations/0004_schema.sql — written, not applied
webc migrate diff --write cover   # … named 0004_cover.sql
sql
alter table categories add column cover_id INTEGER references media_assets(id);
alter table categories add column pinned INTEGER not null default 0;
-- TODO categories.sort_key is not null and has no default: backfill the table and
--   add the constraint by hand, or give the field `.def`
-- note: site_settings.brand_mark is in the table and not in the model (leftover)

It is additive on purpose: a column, a table, an FK reference, a default. It never drops or narrows one — sqlite cannot drop a constraint without copying the table, and a tool that guesses at a data migration is a tool that loses rows. What it cannot infer it writes as a -- TODO line, which is a sentence a person has to answer before the file is applied. Columns in the table that the model does not have are notes, not statements.

9b3. The CRUD every table needs: webc scaffold#

webc scaffold Post writes the four routes a table always gets — list with a search box and a window, new, edit, save, delete — into a file the app owns:

text
src/admin_post.c        the views and the routes (webc/form.h draws the form)
tests/admin_post_test.c one test per route, with the test client (§14b)
webc.json               a line in the "server" set

What it reads is the model, from the app's own descriptor (WEBC_MODEL_DUMP), so the field list, the types, the required bounds and the searchable column are the ones the app actually declares. What it writes is app source: no hidden runtime, no generated file you cannot edit, and nothing that exists is overwritten unless --force. The model is not touched — a scaffold that rewrites your struct is a generator, and generators are the thing this framework does not have. If src/ has a header declaring the model it is included; if the model lives in a .c, the declaration is copied into the generated file (the registry keys on the name, so two copies of one model are one model) with a comment saying a header is the tidier answer.

Then webc check passes on what it wrote, which is the only claim worth making: it builds, its own tests run, and webc lint is clean.

9c. Redis: queues, counters, pub/sub, a lock#

Redis is built in, the way postgres is: <webc/server.h> declares it, libwebc.a implements it, and there is nothing to install and no library to link. The client speaks RESP3 over the same parked sockets every other wait in the framework uses, so a slow Redis parks a task instead of holding a thread — src/redis.c, no hiredis, the same shape as the postgres driver.

c
redis_set("visits:home", "1");                       // a key
i64 n = redis_incr("visits:home");                   // 2 — the counter, atomically
redis_set_ex("session:abc", token, 1800 * 1000);     // … with a TTL in milliseconds
str v = redis_get("session:abc");                    // .p == nullptr when the key is absent
redis_hset("user:7", "theme", "dark");               // hashes
redis_lpush("queue:mail", msg);                      // lists
redis_sadd("online", "user:7");                      // sets
redis_zadd("board", score, "ada");                    // sorted sets
redis_publish("chat", payload);                      // pub/sub

One URL configures it, and it is read the first time the framework asks for a connection, so an app that never touches Redis never opens a socket:

bash
REDIS_URL=redis://:password@127.0.0.1:6379/0
REDIS_URL=rediss://cache.internal:6380/1?pool=8&timeout_ms=200   # TLS
variabledefaultwhat it decides
REDIS_URL—redis://[user:pass@]host[:port][/db][?param=value], or rediss:// for TLS
WEBC_REDIS_POOLone per workerconnections open at once
WEBC_REDIS_ACQUIRE_MS5000how long a call waits for a free connection before it fails
WEBC_REDIS_TIMEOUT_MS500one command, start to finish
WEBC_REDIS_NAMEwebcCLIENT SETNAME, and the namespace the query cache writes under
WEBC_REDIS_TLS, WEBC_REDIS_CA—verify/insecure, and a CA file

redis_open(url) gives a handle you own (redis_close frees it); redis() is the process default, opened from REDIS_URL on first use. A bad URL is nullptr; an unreachable server is a handle whose every call fails. That asymmetry is deliberate: a typo must be caught at boot with a sentence naming it, while a cache that is down must be something the app can survive.

c
if (!redis_ok(redis()))            // configured and the last call worked
  log_warn("redis is down", { "why", redis_error(redis()) });   // never the password

When a command is more than the verbs: the builder is binary-safe and typed, because redis_set(k, v) with const char * cannot carry a NUL and cannot tell an integer from text.

c
WCmd *c = cmd(r, "SET");          // arena-owned, recycled from a small ring
cmd_cstr(c, key);
cmd_raw(c, bytes, len);           // a value with a NUL in it
cmd_i64(c, 42);                   // no snprintf at the call site
WReply rep = cmd_run(c);          // spends the handle; reply_free() when done
if (reply_is_err(&rep)) log_warn("redis said no", { "why", reply_err(&rep) });

A reply is a value tree, not a string: WR_STATUS, WR_STR, WR_INT, WR_DOUBLE, WR_BOOL, WR_ARRAY, WR_SET, WR_MAP, WR_NIL, WR_ERROR — reply_at, reply_val(map, key), reply_double, reply_bool. RESP3's attribute, push and verbatim frames are understood rather than skipped, so a HELLO 3 connection does not desynchronise. A transport failure is a WR_ERROR reply, so a caller reading reply_is_err cannot mistake "the server is gone" for "the key is absent".

WITHSCORES is not flat. On a HELLO 3 connection ZRANGE/ZREVRANGE … WITHSCORES answers an array of [member, score] pairs, not member, score, member, score. Reading reply_at(rep, 0) as the member gets the pair itself — which is neither a string nor an integer, so every number comes back 0 and nothing raises. Read reply_at(pair, 0) and reply_at(pair, 1), and keep a branch for the flat form if the same code may meet a RESP2 server:

c
for (i32 k = 0; k < reply_len(&rep); k++) {
  const WReply *e = reply_at(&rep, k);
  i32 num = reply_int(reply_at(e, 0));    // pair: [member, score]
  i64 hits = reply_int(reply_at(e, 1));
}

N commands, one round trip — the reason a cache and a leaderboard are usable at all:

c
WPipe *p = pipe_new(r);
for (i32 i = 0; i < n; i++) pipe_add(p, "INCR", key);
i32 got; WReply *reps = pipe_run(p, &got);   // in order, arena-owned
pipe_free(p);

Subscriptions own a dedicated connection and one green task, and reconnect with a doubling backoff (100 ms → 30 s), resubscribing on the way back:

c
static void on_msg(str chan, str payload, void *arg) { /* runs on the sub's task */ }
WSub *s = redis_subscribe(r, str_lit("chat"), on_msg, nullptr);
…
redis_unsubscribe(s);   // waits for the task; a subscription that outlives its handler is a leak

Redis pub/sub is at-most-once: a message published while the subscription is reconnecting is lost, and anything that must not be lost belongs in a list (redis_lpush + lpop), not in a channel.

What this client refuses, with a sentence rather than a silent redirect: Sentinel and Cluster (one server, one URL — a client that follows MOVED needs the whole topology story), EVAL/Lua (code in the cache is not something a WebC app should be able to do), Streams (a queue with consumer groups is a data model, and this framework has one), CLIENT TRACKING, and Modules. rediss:// in a build without -DWEBC_TLS=openssl refuses at open, naming the flag: a plaintext connection to a port somebody believes is encrypted is worse than a refusal (§16.5).

9d. The query cache: results in Redis, invalidated by generation#

Every statement in the framework goes through one function, WRes db_exec(), so the cache is one function too. It stores the result set — the same WRes a driver returns — and replays it, which means db_all, db_one, db_by, a view and a test all get a cache without knowing it.

bash
REDIS_URL=redis://127.0.0.1:6379/0
WEBC_QUERY_CACHE=1          # off unless this is set: a cache nobody asked for is a surprise

Nothing to call. With those two variables a select is served from Redis, a write invalidates it, and the app keeps its shape:

c
VecStory *top = db_all_ordered(db, Story, "published desc");   // first: the database
VecStory *again = db_all_ordered(db, Story, "published desc"); // second: Redis, same rows
Story s = { .title = … }; db_insert(db, &s);                    // bumps stories' generation
VecStory *fresh = db_all_ordered(db, Story, "published desc");  // a miss again: the write was seen

What is never cached, because each of these is a wrong answer waiting to happen:

skippedwhy
any write (insert, update, delete, create, drop, and any verb nobody classified)they invalidate; caching a write is not a thing
a read inside a transactionit must see its own writes, and it may be rolled back
a statement with a volatile function (now(), random(), randomblob, last_insert_rowid, …)the answer is not a function of the inputs
a for update / for share readit takes locks; replaying it takes none
/* no-cache */ select …the author says no
anything inside nocache { … }the scope says no
a statement with no tables (select 1)nothing to invalidate it with

/* cache */ select … overrides the volatile rule for a statement you measured, and a number in the hint is that statement's TTL: /* cache 250 */.

Invalidation is a generation counter per table, not a tag set and not SCAN: a write does INCR webc:{<app>}:g:<table> (one hop, O(1), atomic across processes), and a cached read's key carries the generations it was read under — webc:{<app>}:q:<digest>:all=7,stories=12. When the counter moves the key changes, so the old entry is simply never read again and dies by TTL. The app can say so itself, for the changes the database cannot see:

c
cache_bust(Story);   // qcache_bust(Story_modelof()) — after a background job rewrote rows
qcache_flush();      // every entry, everywhere: the big hammer, for a migration
qcache_ttl(Story, 5000);   // this model's rows go stale on their own schedule
variabledefaultwhat it decides
WEBC_QUERY_CACHEoffthe whole feature
WEBC_CACHE_TTL_MS30000how long an entry lives (the backstop for what counters cannot see)
WEBC_CACHE_TTL_JITTER10percent, so a thousand entries do not expire on the same second
WEBC_CACHE_MAX_BYTES262144a result bigger than this is served but not cached
WEBC_CACHE_MS5the cache's own budget per statement; over it, the answer comes from the database
WEBC_CACHE_GEN_MS00 is exact: every cached read checks the counters (two hops). A window reuses the counters it last read (one hop) — and stops seeing other processes' writes for that long
WEBC_CACHE_BREAKER1after three consecutive failures, stop asking for a few seconds
WEBC_TRACE_CACHEoffone line per statement: [cache] select … -> hit

Redis failing never fails a request. Every failure inside the cache is a miss: the statement runs, the page renders, and the cache tries again later. The ladder is a per-statement budget (WEBC_CACHE_MS), a per-command timeout (WEBC_REDIS_TIMEOUT_MS), a breaker, and one log line per transition — measured by tests/qcache_test.c, which kills the server mid-suite and asserts five reads still answer.

The one thing this is not: an HTTP cache. It caches result sets, keyed by the statement and its bound values, not responses — a page that renders from two queries is two entries, and a page whose body depends on the session is nobody's business here.

What it costs, measured on this tree (make bench-cache, WEBC_QUERY_CACHE=1, loopback Redis, sqlite in process):

statementdatabasecache hit
a 20-row select on a 200-row table8 µs270 µsslower: a hit costs two round trips and a parse, so a query cheaper than that is cheaper un-cached
a three-way self-join over the same table119 ms0.27 ms440×

That table is the honest summary: the cache is for the statements that hurt, and on sqlite in process almost nothing hurts — the win arrives with a real database over a network, a big join, an aggregate over a million rows. WEBC_CACHE_GEN_MS halves a hit (0.27 ms → 0.14 ms) by dropping the counter check. A hit is visible in /debug and in qcache_stats():
