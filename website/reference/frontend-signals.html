11. Frontend: signals

Reference · docs/reference.md

c
state(int, count, 0);           // get(count) / set(count, v)
computed(int, doubled) { return get(count) * 2; }
effect(log_it) { printf("%d\n", get(doubled)); }
batch { set(count, 1); set(count, 2); }   // one effect run
  • Writing the same value does not re-run effects (byte comparison).
  • Effects run in topological order, once per batch.
  • signal, computed and effect declare file-scope statics (they define functions),

    so they do not work inside a function body.

  • That makes them one per translation unit: right for app-wide state, wrong for a

    view that appears twice on a page. For that there is the _in family below, and for a list there is state_own (§11c).

Three declarations, one rule between them — what is the state one of?

declarationone value peryou reach it withfits
state(T, n, init)page (translation unit)get(n) / set(n, v)the app's own state
state_in(T, n, init)WInst you createget_in(&inst, n), or get(n) inside with_insta view mounted N times by your code
state_own(T, n, init)render positionget(n) / set(n, v)a row of a list, a mounted view's own copy

11a. What re-renders a view (and what does not)#

The one thing every client author asks first, because the answer is not "the signal":

A render follows every action and every host callback. The bridge re-renders each mounted view — and diffs it — when control returns to it: after a click, after a typed field, after a webc_later timer fires, after a fetch or an SSE frame settles, after a push_url-driven nav. Writing a signal does not by itself schedule a render; the flush point is the bridge boundary.

So an action never has to "touch the view":

c
action(toggle, Todo *t) { t->done = !t->done; }   // the view runs again when this returns

There is no tick signal to bump, and a set(tick, get(tick) + 1) is a write nobody reads — the render would have happened anyway. What a render costs is a different question: the whole view runs again, so keep expensive work out of it — that is what §12b2's jobs are for.

The exception is the one §12j adds: a node the view declared as live (text_live, attr_live, class_live, show_live) is written in place when its signal changes, and an action marked action_live skips the render entirely. Everything structural — if, for_each, part, markup(), a new node — still needs the render.

webc check --wiring also names the trap this rule creates for lists — a live binding on a page-wide signal inside a for_each (every row then shows the same value, which is what state_own in §11c is for) — and it knows state_own, so the never-read rule below still applies to it.

webc check --wiring notes a signal that a write feeds and nothing else reads, because that is exactly what a leftover tick looks like: set(tick, get(tick) + 1) reads the signal it writes, which is why a plain "never read" rule misses the idiom the framework teaches (set(tick, get(tick) + 1)). The check counts a read that happens on a line with no write of the same signal, so the self-feeding write is not mistaken for a reader.

11b. The store: frames in, generations out#

A live document arrives as frames (a seed, then a stream), and each frame's strings must die when the frame two later replaces it. WStore owns that rotation — the ~100 lines every streaming client would otherwise write first:

c
static WStore room;                                        // once
store_init(&room, BoardDoc_docof(), sizeof(BoardDoc));

BoardDoc *d = store_read(&room, frame);  // NULL = a bad frame; state unchanged
// d lives until the frame after next; ref() reads find it (wc_ref_epoch is set)

store_cur() is the live document between frames, store_arena() the generation it lives in; store_free() returns everything. The server twin is WFrame (§7d).

Per-instance signals#

The same declarations, but the state lives in a WInst you own, so the same view can exist any number of times:

c
state_in(int, count, 0);                       // get_in(&inst, count) / set_in(&inst, count, v)
computed_in(int, doubled) { return get(count) * 2; }
effect_in(log_it)        { printf("%d\n", get(doubled)); }

view(Card) { el("span") { text("%d", get(count)); } }   // get(): the ambient instance

WInst side, page;                               // two cards, two counts
winst_init(&side, nullptr);                     // nullptr = heap; an arena also works
winst_init(&page, nullptr);
set_in(&side, count, 3);
with_inst(&side) { html1 = wcomp_html_ctx(&c1, view_Card, nullptr); }
with_inst(&page) { html2 = wcomp_html_ctx(&c2, view_Card, nullptr); }   // renders 0
mount_in(log_it, &side);                        // effects are started per instance
winst_free(&side);                              // kills its nodes; nothing left behind
  • get / set reach the instance bound by with_inst, and panic outside one:

    a per-instance read that cannot know which copy it means is a bug, not a default. Where there is no ambient instance — an action, a test, the other card — name it: get_in(&inst, count). There is no second spelling: get reads a signal whether it lives in the process or in an instance, and picks the right one.`

  • Instances are values. winst_init(&x, nullptr) is heap-backed and winst_free

    returns every byte; winst_init(&x, arena) allocates from the arena and needs no free, but must not outlive it.

  • CELL(T) + cell_init / cget / cset is still there for one signal inside a

    struct you already have. WInst is for a whole view's worth of state.

11c. Per-row state: state_own#

A list is where local state lives — a row's open flag, a row's draft text, a row's quantity — and a row has no name to hang a WInst on. state_own is the declaration whose owner is the position that drew the node: the for_each row, or the mounted view. (A view rendered into an email is a third — one render, its own copy, discarded after — so a view with per-row state can be both a page and a mail part.)

c
state_own(i64, qty, 0);
state_own(bool, open, false);
state_own(Text, label, "");
computed_own(i64, twice) { return get(qty) * 2; }

view(Line) {
  el("tr") {
    el("td") { text_live("%lld", qty); }          // this row's value, live
    el("td") { bind_str(label); }                 // this row's field
    el("button") { named("bump"); text("+1"); }
  }
}
// client: bind("bump", "click", bump);
action(bump) { set(qty, get(qty) + 1); }          // the row the clicked button drew
  • Identity is (position, declaration). Two rows are two values; the same view mounted

    twice is two values, with no plumbing at all. A row that moves in a keyed list keeps its value, because the position is the key.

  • A live binding may target it. text_live, attr_live, class_live and show_live

    all take a state_own name — one write, one op, the row the action belongs to and no other. This is the part state_in cannot do (a WInst signal is refused, §12j) and the part that makes a 1 600-row table interactive.

  • An action resolves it through the node it came from. The bridge knows which element

    the event carried a hook for, and pushes that element's owner before the action runs; so get(qty) means "the row of the button that was clicked", not "the row rendered last". get_N() / set_N() are the same thing spelled out, for code that is inside a row body.

  • Lazily created, disposed with the position. A row that never reads its slot allocates

    nothing; the keyed sweep, wcomp_destroy and the component's own render kill the slots with the row. Cost when it is used: ~184 B per live row (WInst + one node per declaration), so a 20 000-row table with per-row state is still the wrong shape (§16.8).

  • Reading it outside a position panics, naming the declaration — the same rule as

    state_in: a per-position read with no position cannot know which copy it means. state(…) is the declaration for "one value, anywhere in the page".

  • The server half is unchanged. SSR draws the declaration's initial values and registers

    nothing, so hydration is byte-for-byte what it was.

  • state_own and state_in answer different questions and both can be live in one app: a

    position resolves first (state_own), and with no position in scope with_inst answers (state_in).

toggle(name) flips a flag in place — set(x, get(x) ? 0 : 1) written out is an inversion the reader decodes; the macro is the name of the thing. And state(T_, N_, …) is generic: state(bool, ahead, false) works, and a flag that is a boolean reads as one in an if instead of carrying a comment that says which integers mean what.

11d. Component instances: comp()#

state_own is one value per render position, and a position is a mounted view or a for_each row. That leaves the unit a component author actually writes — the call — without one: a PART is a plain C function, so calling it pushes no position and two calls of one part in the same view shared one slot. comp() says which call is which:

c
state_own(i64, qty, 0);

PART(Stepper, (label, Text));
void Stepper(Text label) {
  el("div") { class_("stepper");
    el("button") { named(fmt("dec-%s", label)); text("−"); }
    el("span")   { text_live("%lld", qty); }       // this call's slot
    el("button") { named(fmt("inc-%s", label)); text("+"); }
  }
}

view(Order) {
  el("main") {
    comp(Stepper, "Chairs");   // its own qty
    comp(Stepper, "Tables");   // and this one's
  }
}

action(inc_chairs) { set(qty, get(qty) + 1); }     // the instance of the button clicked
  • Identity is (the position that drew it, the call site). The call site is a

    __COUNTER__ captured where comp() was written, so the same call on the next render finds the same instance, two calls never share one, a row that moves in a keyed list keeps its components, and a branch that stops drawing one disposes it.

  • Nothing is allocated for a component that asks for nothing. The instance is created

    the first time a state_own/computed_own is read or an effect_own is started, and killed when the position is swept (the sweep is the keyed list's, keyed by call site).

  • Everything downstream already resolves the instance, because it resolves the node's

    owner: text_live/attr_live/class_live/show_live, bind_str, input_hook, and every action (get(qty) in an action means "the instance of the button that was clicked", exactly as it means "the row" inside a for_each).

  • It is opt-in. A part called without comp() keeps the older rule — it draws in the

    position that called it, so its state_own is shared with every other call in that position. That is what makes the change additive, and webc check --wiring points at the parts where it matters: a part that declares state_own and is called twice in one function gets a note naming both, which comp() at the call sites clears.

  • No wrapper element. comp() is a position, not an element: the part's markup is a

    direct child of whatever element it was written in, so CSS sees the tree you wrote.

  • SSR is unchanged. The server draws the declaration's initial values and releases the

    instances when the html is text; the browser builds its instances from the same call sites, so hydration is byte-for-byte what it was.

Lifecycle: effect_own, mount_own, on_cleanup, on_mount#

An instance is worth little without a way to clean up after it, and the framework had no per-position effect and no teardown hook at all:

c
effect_own(save) {                        // file scope: the body
  webc_later(800, flush_draft);           // one timer per instance, not one per page
  on_cleanup(cancel_pending);             // before the next run, and when the instance dies
}

view(Editor) {
  mount_own(save);                        // start it in *this* position; idempotent
  on_cleanup(drop_draft, nullptr);        // once per position, registered on its first render
  el("textarea") { bind_str(draft); }
}
  • effect_own(N_) { … } declares an effect that belongs to the ambient position; the

    body runs with that position bound, so get/set work as they do in the view. mount_own(N_) starts it, once: a second call on a later render is a no-op, which is what lets the line sit in the view body. (An effect body cannot be spliced into a view — there are no closures — which is the whole reason the pair exists, the same pair effect_in + mount_in already had with the app owning the lifetime.)

  • on_cleanup(fn, ctx) inside an effect registers with that run — it runs before the

    next run and when the effect is disposed. Outside an effect it registers with the position, on the position's first render only (a view that re-renders sixty times a second must not register sixty teardowns for one subscription).

  • on_mount(fn, ctx) runs once, after the batch that drew the position has gone out —

    which is when the node it wants to focus or measure exists. It is a client gesture: a server render queues nothing, and a native test runs the queue with wc_mount_run() after calling wc_client_mode().

  • winst_release is recursive: an instance's children are torn down first, with the

    parent still intact, so a nested component's cleanup can read the state it was drawn in.

11e. Children: WKids#

A function cannot take a block, so a component that wraps other markup takes a callback and a context — the (fn, ctx) pair wkeyed_list and prose_with already use:

c
PART(Card, (title, Text), (inner, WKids));
void Card(Text title, WKids inner) {
  el("section") { class_("card"); el("h3") { text(title); } kids(inner); }
}

static void body(void *ctx) { el("p") { text("%s", (char *)ctx); } }
comp(Card, "Hello", kids_of(body, msg));

kids_of captures the position that wrote the call (the component's parent), so a state_own read inside the children block is the caller's — React's rule too: children are created by the parent. no_kids is the empty value, so an optional body is kids(inner) where inner may be {0} and nothing is drawn.
