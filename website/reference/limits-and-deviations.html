Docs/Reference/16. Limits and deviations

16. Limits and deviations

Reference · docs/reference.md

These are measured facts, not guesses:

  1. No nested functions. C23 removed them, so routes() cannot contain GET(...).

    Routes are file-scope macros; grouping is done with path prefixes and per-route middleware (GET_MW).

  2. Bare qualifier flags are invalid C. .required is a syntax error; write

    .required = true. There are no token-pasting macros named required/max, because a macro that turns a field into a flag cannot be read back by the compiler's own message.

  3. state(...) shadows state(2) in any translation unit that includes

    <webc/web.h>; select(...) shadows select(2) the same way, and that one predates it. Include the system headers first. Neither is a problem in a translation unit that does not call the POSIX function — and a file that does can call select_wait (see task.h) or keep the system header in its own translation unit.

  4. No guard page on task stacks. mprotect(PROT_NONE) on one page of an anonymous

    mapping makes its neighbours SIGBUS on Darwin (verified with isolated repros), so overflow detection is by fault, not by message. A canary at the stack base fires falsely on every task because Darwin's ucontext writes its own frames there.

  5. Redis is one server, one database, one process pool. No Sentinel, no Cluster, no

    MOVED redirection, no SCAN-driven invalidation: the query cache's counter keys and entries assume a single server everybody shares. A Cluster deployment is a different client, not a configuration of this one.

  6. TLS is a build feature, off by default. -DWEBC_TLS=openssl (OpenSSL headers

    and libraries; make tls-test) enables res_tls/tls_connect. A build without it refuses to start when a listener is configured for TLS instead of serving plaintext on a port someone believes is encrypted. Postgres has no TLS, so sslmode is not implemented.

  7. The wasm target needs wasi-sdk (~170 MB, a separate download; webc doctor

    reports whether it found it). The browser half has no threads, no filesystem and no SQL: include/webc/web.h is the subset it compiles — core, collections, models, JSON, signals, DOM. Verified end to end in Chrome: render, keyed list add/remove/toggle, two-way bound input, SSR markup hydrated in place.

  8. Postgres and MySQL are wired and tested — make pg-test starts

    postgres:16-alpine, make mysql-test starts mysql:8, each runs the same suite across every driver, and each removes its container. Postgres was untested for most of this build; the SQL lexer and the driver twins were found by running it. Only PG16 and MySQL 8 are tested — MariaDB gets the same protocol but not its own run, there is no PREPARE reuse on the postgres side, and there is no pool-exhaustion test for either. The MySQL driver has no RSA public-key exchange, so sha256_password and caching_sha2_password's full authentication need TLS.

  9. A component instance costs 56 B, and comp() is opt-in. One heap WInst (24 B) and one

    table slot (32 B) per instance drawn, whether or not it reads state; a part called without comp() pays nothing and shares its position's state (§11d). The 20 000-row table with a component per row is therefore still the wrong shape — per-row state is the same arithmetic.

  10. wcomp_render re-renders the whole view and diffs. That is component-level

    reactivity, not per-node: the DOM writes are minimal, the C work is not. §12j's live bindings are the per-node half — a leaf the view declares once — but they do not make a structural change cheap, and they do not raise the 20 000-op mount budget (§16.8).

  1. webc_serve runs one worker per core by default (cpus = 0 → the online

    processor count, capped at 64; set cpus = 1 to force a single worker). A task may be resumed on a different worker than it started on, so request state and the current arena travel with the task, never in a thread-local (webc_req_current(), wtask_local(), and the scope accessors below). Measured with make load on a 10-core machine: 16 780 req/s of SSR HTML at 16 keep-alive connections and 12 112 req/s of one-request-per-connection churn, zero errors and no leaked connections or tasks over ~260 000 requests. The bugs that had to be fixed first are in findings/scheduler-and-server-bugs.md.

  1. Request state is task-local, not thread-local. If you add an API that

    needs "the current request", the markup build in progress or a per-request arena, use the task-local accessors (webc_req_current(), wbuild_current(), and the scope arena the framework installs) — never an arena of your own. A _Thread_local there is a bug: many tasks share a worker thread, and a task that parks resumes on another one. wbuild_current() cost a real outage — examples/todo reads the database inside its view, the task parked there, and every worker began answering 500 "el() outside a build"; one render then dereferenced the null and the process died with SIGSEGV at address 72.

  1. A request allocates nothing that outlives it. The body, headers, params

    and rows live in the request arena; the render's component (three arenas and a command buffer) is destroyed before the response is written; a log line allocates nothing at all. Measured: /metrics webc_heap_bytes is byte-for-byte identical before and after 130 000 SSR-with-database requests, and 95 000 text requests; webc_arena_bytes is flat. RSS settles around 11 MB on that workload (allocator retention, not growth). Benchmarks print B/op for exactly this reason: it read 3 200 B/op the hour it was added.

  2. arena_destroy gives back what it took. wm_stats().arena_live counts

    chunks that exist, not reservations. Double-counting and keeping the reservation of an arena that never allocated is how /metrics comes to report 9 GB of live arenas after 300 000 requests.

  3. webc_test_request()'s Response lives until the next call on that

    thread: the helper resets a per-thread arena instead of allocating one per call (which leaked 64 KB per request in a loop). Copy what you keep — the suites in examples/ show the pattern.
