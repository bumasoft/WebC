14. The CLI

Three of those are about not lying to yourself:

webc build --explain prints the object cache's reasoning ([stale] src/view.c: …deps sub.h mtime=…, [cc] src/view.c) instead of compiling in silence. WEBC_TRACE_WATCH still elsewhere-documented what the dev server watches; this is the build's own account, as a flag, because the moment somebody needs it is the moment they are staring at a build that did the wrong thing.

A failed build clears the cache and tries once more. A cache that is stale in a way mtimes cannot see — a restored checkout, a header touched back in time, a killed build's half-written object — presents as a compile error in a file that compiles, and the cure is rm -rf .webc. A failing build now says so, clears the object directory and rebuilds; if the second attempt fails too, the errors are real. The wasm half falls back to the one-shot command and clears its own object directory, so the slow path repairs the fast one instead of masking it once.

webc size answers "what does this page cost, and where did it go" without devtools:

    module  .webc/app                   1.77 MB    69.0 KB gz
    bridge  assets/webc.js              62.5 KB    19.3 KB gz
    sent over the wire (both, gzipped):  88.3 KB

    where the module goes:
      code                               140.9 KB   7.8%
      data                                1.62 MB  91.9%
      custom (names, debug, producers)     5.0 KB   0.3%

    the biggest statics (from the object files):
      g_strats                            1.60 MB
      …

    A static declared without an initialiser is zero-fill and costs no bytes; one with an
    initialiser ships its zeros. Compare the list with the data section above: the static
    about that size is the one being paid for, and filling it in boot() moves it to zero-fill.

That output is not a demonstration: the command, run on a real app, finds 1.6 MB of data that turns out to be one static Strat g_strats[] = {…} — 21 partially-initialised structs holding 10 001 doubles each, whose zeros a wasm data segment ships byte for byte. Declaring it without the initialiser and filling it in boot() takes the module from 1.77 MB to 165 kB. Nothing else in the framework's tooling can tell you that.

webc.json:

json
{ "name": "myapp", "version": "0.1.0", "entry": "src/main.c",
  "database": "sqlite:data/dev.db", "port": 8080,
  "dev": { "port": 9999, "connect": ["https://api.example.com"] } }

dev.connect is the Content-Security-Policy connect-src the dev server sends: a browser half exists to call somebody's API, and webc dev serves that half, so the dev policy already allows any https: origin. Name the origins your app actually calls and the policy becomes exactly those (plus the reload websocket) — a narrowing knob, never a widening one, and it only ever applies to webc dev.

14d. The language server#

webc lsp speaks LSP over stdio, from the same binary as the rest of the CLI: no Node, no second download, no build. Point any editor at webc lsp and it has diagnostics, completion, hover, definition, references, an outline and quick fixes for a WebC project.

It is two engines with one line between them, because a WebC file is two things at once. C is clang's job — a whole view type-checks in about a tenth of a second, and a second hand-written C front end would be a second source of truth about C. The DSL is ours: the macros that take a following { … }, the model tuples, the three file sets, the routes, the wiring. A per-file region map — which bytes are inside view(…), el(…), GET(…) and which are plain C — decides which engine answers a given caret.

That translator is the product. The compiler answers page(Nope, …) with use of undeclared identifier 'view_Nope' behind five frames of WC_CAT; the server answers "no view named Nope in this project — view(Nope) draws it, or declare_view(Nope) in the shared header announces it", and offers the line to add. GET(…) in a shared source is a caret error naming the half, not eight cascading syntax errors about parameter declarators.

The compiler half is the same compiler webc build runs, asked about the buffer the editor is holding rather than the file on disk. Two rules keep it from being a second opinion: a diagnostic inside a DSL macro's own parentheses is dropped (those bytes are the WebC engine's to explain, and the compiler speaks about them in names like view_Nope), and a block that never closed stops the compiler from running at all. WEBC_CC picks the compiler; when a project's check costs more than 120 ms it moves from every keystroke to every save, because a language server that stutters is a language server people turn off.

What it knows, it knows from the sources: the models (including the ones declared in headers, which no webc.json ever lists), the views and where they are drawn, the actions and what is wired to them, the routes and the view each returns, and which standard-library module may appear in which half. Nothing under .webc/ is read, so a fresh clone is a working workspace.

It deliberately does not reformat a view. clang-format rewrites el("h1") { text("Todos"); } into four lines, which is not this language's style; document formatting is therefore refused with a reason, and range formatting outside a DSL block is what webc lsp offers instead.

There is a second opinion in most C editors, and it is clangd. So the server writes compile_commands.json at the project root — the flags webc build uses, one entry per source — which clangd finds without being told anything. Without it clangd invents errors on a WebC file it cannot resolve; with it, the twenty-one it invented in this repository became none. The file is generated, gitignored, and the server never reads it back.

The editor client lives at editors/vscode/: no dependencies, no build step, nothing required from a registry. Where the binary is comes from resolve.js — the setting with ~ and ${…} expanded, else build/webc in the workspace or a parent, else the PATH — because a settings field is typed by a human and spawn(2) expands no tilde. make lsp checks that the client still loads and that the resolver is right about every way a path can be wrong (missing, a directory, not executable, relative, on no PATH), so a client that silently ignores the setting is a red gate rather than a broken window.

make lsp is the gate: --selftest asserts what the server says about a real project, and --replay diffs the protocol against a recorded session (tests/lsp/sessions/*.jsonl), so a wire change is a diff in review rather than a bug report. --bench prints what one request costs, and --trace FILE writes every message it saw as JSONL.

14e. The VS Code extension#

editors/vscode/ is that client: extension.js speaks JSON-RPC to webc lsp over stdio itself (no vscode-languageclient), and resolve.js decides which binary to spawn. It is three settings and two commands:

settingdefaultmeaning
webc.lsp.path""the binary. ~, ${workspaceFolder}, ${userHome} and ${env:NAME} are expanded; a relative path is taken from the workspace folder; empty means build/webc in the workspace or a parent, else webc on the PATH
webc.lsp.args[]extra arguments, e.g. ["--trace", "/tmp/lsp.jsonl"]
webc.lsp.enabledtruestart the server at all
commandwhat it does
WebC: Show the language server logthe output channel, including every diagnostic the server published
WebC: Restart the language serverrespawn, without reloading the window

It spawns <bin> lsp --root <workspace> <args>, clears its diagnostic collection whenever the server stops (a dead server must not leave yesterday's errors on screen), and re-reads its settings on change — a setting that is only read once at activation is indistinguishable, from the outside, from one that is ignored. A failed start is one message that says which failure it was (not found, not executable, exited) and quotes the last lines of the server's stderr, with the resolved path in it.

Installation is a copy, a symlink, or a .vsix; code --extensionDevelopmentPath= "$PWD/editors/vscode" runs it out of the tree. The guide The editor has the commands for VS Code, Cursor, Antigravity, Neovim and Emacs, and the troubleshooting table.

14f. The MCP server#

webc mcp speaks the Model Context Protocol over stdio, from the same binary as everything else — no Node, no second download, no version skew between the server that answers and the compiler it answers about. The argument is the one that gave us webc lsp, and it is stronger here: a server that reports diagnostics must be the compiler.

It exists for one reason, stated as four:

What an agent needsA shell already gives itWhat MCP adds
the gate, after a changewebc check{ok, steps:[{name, ok, output}]} — no prose to parse
the project's own indexgrepmodels, fields, views, actions, routes and each file's half, with positions
the whole public surfacegrep api.txta search that returns the declaration, its header and its doc line
the page it just builttwo processes and curla dev server held across calls, and webc_fetch

Seven tools, and one rule: every tool is a door onto something the CLI already does, and nothing parses human output. If a tool needs data, the command that owns it learned --json first. That is what keeps this from becoming a second, disagreeing front end.

toolreturnswrites
webc_checkthe --json gate: build, tests, doctor, boot, schema, routes, lint, consistency—
webc_factsmodels (+fields, qualifiers), views (+context), actions, routes (+view), files (+half, modules)—
webc_api{query} → matches:[{header, line, declaration, doc}]—
webc_test{filter?} → {ok, tests:[{suite, passed, failed, output}]}—
webc_dev{action: start|stop|status} → {running, url, port}; one server held by the process✔ process
webc_fetch{path, method?, body?} → {status, content_type, body} from that server—
webc_scaffold{template, dir} or {add_module} → what was written✔ files

Resources: webc://project (the index, refreshed on read) and webc://reference (the heading index of this document, so a reader can ask for §9a2 instead of loading 3 392 lines).

Point a client at it:

json
{ "mcpServers": { "webc": { "command": "/path/to/WebC/build/webc", "args": ["mcp"],
                            "cwd": "/path/to/your/app" } } }

webc mcp --selftest is the gate: it runs a scripted session against examples/todo and asserts what the tools answer — the same shape as webc lsp --selftest, for the same reason (a protocol change should be a failing test, not a bug report). make mcp runs it.

--root defaults to the working directory, which is what a client passes as cwd; if that directory has no webc.json but one of its ancestors does, the nearest project wins, so a session started in src/ still answers about the app. With no project anywhere above, the directory given is used and the tools report a project with nothing in it.

Two knobs worth knowing: the dev server's own output goes to .webc/mcp-dev.log (stdout is the protocol channel and a stray banner corrupts every message after it), and webc_dev refuses to start over a build that does not compile — a serve that quietly serves the last good binary is the most confusing way to learn your change is broken.

14g. Working with agents#

Three surfaces, and each is authoritative for a different thing. The rule that keeps them from disagreeing: a contract is written once and the other two are generated from it or call it.

SurfaceAuthoritative forKept honest by
docs/reference.md, the site guideswhat is truereview; webc lint --all over the docs
skills/webc/what to do, and where to readmake skill-check: regenerated from the docs
AGENTS.md (scaffold and repo root)the gate to run, and the four mistakes to avoidwebc lint --all; a scaffold test builds and checks every template
webc mcpthe same answers as datamake mcp: a scripted session, asserted

The documentation in an app. webc new writes the skill — SKILL.md and its references/ — into the app's .webc/docs/, and the scaffold's AGENTS.md names it. The argument is the one this section is about: an agent inside an app must not have to find the framework's sources to answer "what does this name do", and a session spent grepping a checkout for auth_hash_password is the failure that put the files there. .webc/ is gitignored, so the copy is never vendored and never stale; webc docs rewrites it, webc docs --list names the topics, webc docs <topic> prints one, and webc api <query> answers the narrower question (the declaration, its header and the doc line above it) from the headers this binary was built against.

AGENTS.md. webc new writes one into every scaffold: webc check as the gate, the half rules (db_*, req, path*, query, body are server-half names), one WEBC_MODEL for struct/validation/JSON/SQL, fmt() and persist(), migrations, and "believe webc lint". The repository root has its own, for a different reader: the gates, the house rules (one scanner, one index, one set of diagnostics; the api ratchet; a budget is a gate; machine output is a contract) and the layout. Neither is generated — they are short on purpose, and a change to either is a change to what every agent does next.

The skill. skills/webc/SKILL.md is written by hand: the five ideas, the loop, the project shape, recipes, the rules that bite, and a routing table into references/. The fourteen leaves under skills/webc/references/ are generated by tools/gen_skill.py from website/src/content/guides/*.md, anchored sections of this document, and webc lint --rules (traps.md). Generation is the whole argument: a skill that teaches a retired spelling is a language nobody can compile, delivered with confidence, and this framework has retired forty-six of them and deleted a render macro outright; webc lint --rules is the table, and the table is the count.

make skill regenerates; make skill-check is the gate, in three parts:

PartFails when
tools/gen_skill.py --checka leaf would change — the documentation moved and the skill did not
webc lint --skill skills/webcthe skill's own prose names a retired spelling (generated leaves are exempt: they quote this document, which is gated where it lives)
website/tools/snippets.pya c block in a skill does not compile, has an ellipsis, or has no leading comment saying which file it is

Machine output. A command with a --json face renders what it did; it is never a second implementation. check, test, routes, doctor, api, stdlib, size, lint and explain have one (§14's command table has the shapes). Terminal behaviour is a contract too: colour is off when stdout is not a terminal, NO_COLOR is set, or TERM=dumb is (with WEBC_COLOR as the override); a failed build prints once, after one cache-cleared retry, without the compiler's command line (WEBC_VERBOSE restores it); and a failed build calls the translator automatically, so webc build and webc check say the same sentence about the same mistake (WEBC_NO_EXPLAIN turns that off). A tool never parses human output — if a tool needs data, the command that owns the data learns --json first.

webc explain. It reads the compiler's path:line:col: error: lines, asks the same engine the language server uses what that line is, and prints one sentence per mistake — deduped per file:line, wrapped at 92 columns at the sentence's own indent, so a transcript and a terminal agree byte for byte. --project skips the build and reports every finding in the sources; --raw also prints the compiler's own output, untranslated, for when the translation itself is what is wrong. It refuses to run over the framework checkout: that tree is a hundred example apps, not an app.

The narrative version of this section — the loop, the two failures, the install — is the site's agentic coding guide.
