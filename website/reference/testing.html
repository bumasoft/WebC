Docs/Reference/14b. Testing

14b. Testing

Reference · docs/reference.md

webc test compiles each tests/*_test.c into its own binary (with the app's own sources linked in, its main renamed), runs it, and prints go-test-shaped output. The surface is <webc/test.h>:

c
#include <webc/test.h>

TEST(creates_an_account) {
  Response r = webc_test_request("POST", "/accounts");
  ASSERT_EQ(r.status, 201);
  Account a = { .email = str_lit("ada@example.com") };
  ASSERT_OK(model_validate(Account_modelof(), &a, nullptr));
}
  • TEST(name) { } — a test. It registers itself with a constructor, so a file

    is a list of blocks and nothing is enumerated by hand. No main, no list to forget.

  • TEST_MAIN() — the binary's entry point. TEST_SETUP(fn) /

    TEST_TEARDOWN(fn) run once around the file (a database, a scheduler).

  • SUBTEST("label") { } and SUBTESTS(rows) { ... } — a subtest is one

    block; SUBTESTS runs the block once per row of a static array, binding the row to r and using its name member for the label. A failing row does not stop the next one.

  • Assertions: ASSERT, ASSERT_TRUE/FALSE, ASSERT_EQ/NE/LT/LE/GT/GE,

    ASSERT_FEQ, ASSERT_STR_EQ (a str/Buf/Response/C string against a literal), ASSERT_STR (two of them), ASSERT_STR_CONTAINS, ASSERT_MEM_EQ, ASSERT_NULL/NOT_NULL, ASSERT_OK/ERR/ERR_KIND (anything with .ok). An assertion records a failure and continues, like go's t.Error.

  • Responses: pass one straight to ASSERT_STR_CONTAINS(r, "…"), and read a header

    by name: ASSERT_STATUS(r, 303), ASSERT_HEADER(r, "Location", "/"), ASSERT_HEADER_CONTAINS(r, "Set-Cookie", "HttpOnly"), ASSERT_HEADER_COUNT(r, "Content-Security-Policy", 1), ASSERT_BODY_LEN(r, 12). A duplicate header is legal HTTP and a real bug; counting is the only way a test can see it. Header names are matched case-insensitively (RFC 9110 §5.1): a handler stores Set-Cookie as it spelled it, and a test may ask for set-cookie — a memcmp comparison misses it, which is why every app that asserts on a session cookie writes its own helper.

  • FAIL(fmt, ...) records a failure with a message; SKIP(why) stops the

    test and reports it skipped.

  • try(expr) inside a test panics with the error (a TEST body returns

    void, so it cannot return the Result); the runner turns that into a failed test with the message. Every test runs inside a panic frame, so a panic in application code — not just in an assertion — fails that one test and the rest of the file still runs.

The client half of a test. A request with no memory is not a browser, and a test of a mutating route written without one rebuilds a browser: a cookie jar by hand, a form body by hand, and a helper for the header lookup. TestClient is that browser (§14b1 below):

c
TEST(the_save_route_writes_the_row) {
  TestClient c = test_client();                       // a jar, per test
  Response r = tc_post_form_at(c, "/admin/posts/save", Post, &draft);
  ASSERT_REDIRECT(r, "/admin/posts");                 // 302/303/307 *and* the Location
  ASSERT_DB_ONE(Post, slug, str_lit("the-last-ferry"));  // the row it should have written
  ASSERT_DB_COUNT(Post, 1);
}

What is actually asserted, spelled out: webc_test_request(method, path) builds a request, runs the router and the middleware chain, and returns the Response — no sockets. webc_test_request_ex(method, path, headers, body, body_len) is the same with a header block ("Cookie: session=…\r\n") and a body, which is what a test of an authenticated route needs. Both convert a handler panic into a 500, exactly like the server.

An app's tests link the app. webc test compiles the app's sources (found the same way webc build finds them) with main renamed, so the routes are the real ones; the state is built by calling the app's own webc_boot() from TEST_SETUP() (<webc/app.h>). examples/todo and examples/accounts are the worked examples: 8 and 7 tests, real database, real sessions, no socket.

14b1. The test client: a jar, a form encoder, and the row#

c
TestClient c = test_client();                      // the current test's arena; nothing to free
Response r = tc_get(c, "/admin");                  // GET, with the jar's cookies attached
Response p = tc_send(c, "PATCH", "/admin/posts/1");// any method
r = tc_post_body(c, "/theme", str_lit("to=dark")); // a body of your own
r = tc_post_json(c, "/api/posts", Post, &p);       // the model, as JSON
r = tc_post_form_at(c, "/admin/posts/save", Post, &p);  // the model, as the form it would draw
  • The jar. Every Set-Cookie the response carries is kept (name and value, not the

    attributes) and sent back on the next request; Max-Age=0 deletes one. A second test_client() in the same test is a second browser — the two-users case, which was untestable when a test could only send headers it had spelled itself.

  • The form encoder. tc_post_form* serialises the model the way model_from_form reads

    it: one input per field in declaration order, the pk left out (a create does not post the id back), a bool as on/off, an enum as its value's name, a VecStr as one comma-separated value, and everything percent-encoded as a browser encodes it.

  • The assertions a mutation test needs. ASSERT_REDIRECT(r, "/where"),

    ASSERT_DB_ONE(T, field, str) / ASSERT_DB_ONE_I64(T, field, n) ("the row it should have written"), ASSERT_DB_COUNT(T, want).

It does not run JavaScript — that is webc test --client, which replays the client half's batches through the real bridge — and it does not follow redirects: a test that follows one hides the 303 it came for.

webc test --watch reruns the suite whenever src/, tests/, shared/, content/ or webc.json changes, clearing the screen each pass, so what is on it is the last run and not the history of them. --filter picks suites (and runs them whole); --test narrows by test name across every suite, which is the slower one because every suite builds.

14c. Assertions about structure#

A substring test passes when the markup moved somewhere the CSS no longer reaches — which is exactly the regression a redesign causes. Two assertions speak the languages a response is actually written in:

c
ASSERT_JSON(res, "data.0.views", "42");                       // by path
ASSERT_JSON_STR(res, "data[0].slug", "the-last-ferry");
ASSERT_HTML(res, "article.lead > h2 a");                      // the structure survived
ASSERT_HTML_TEXT(res, "article.lead > h2 a", "The chair nobody notices");
ASSERT_HTML_COUNT(res, "article.card", 6);
ASSERT_HTML_ABSENT(res, "article.lead");

The selector is a subset of CSS: tag, .class, #id, [attr], [attr="value"], descendant (space) and child (>). wc_json_path(JVal*, "a.b.0", &out) and wc_html_count(html, sel) are the functions underneath, for a test that wants the value rather than the assertion.

Structured data is neither JSON nor HTML, and it is the thing that breaks silently — a page whose author gained an empty name still renders, still passes ASSERT_HTML, and has quietly lost its rich result. ASSERT_LD reads the first application/ld+json block out of a page and asks it the same by-path question:

c
ASSERT_LD(res, "headline", "The last ferry");
ASSERT_LD(res, "author.name", "Ada Okafor");
ASSERT_LD_ABSENT(res, "datePublished");     // a draft has none, and the key is not ""
ASSERT_JSON_DOC(doc, "publisher.logo.url", "https://example.com/logo.png");  // a document you built

ASSERT_JSON_DOC / ASSERT_JSON_DOC_ABSENT are the same question about a JSON document rather than a response — what a serializer, a writer, or a ld_* call is tested at, before a route exists. wc_ld_block(html) returns the payload if a test wants it directly.

An HTML assertion matches the server-rendered markup with its data-wc anchors in it, so it tests the page a browser receives, not a string this test happened to expect.

Every one of them takes any HTML-ish thing, not just a Response: a str from wcomp_html_ctx (the browser half's own render), a Buf, a const char *. That is the whole of what a client-side test needs to read a card:

c
str html = wcomp_html_ctx(&comp, view_Stats, nullptr);
ASSERT_HTML(html, ".card.ruin b");
ASSERT_HTML_TEXT(html, ".card.ruin span", "ruined");
ASSERT_HTML_NUMBER(html, ".card.ruin b", 96.3);   // "$10,038" reads as 10038, "4.2%" as 4.2

ASSERT_HTML_NUMBER is the one that replaces a hand-written scanner per app: it takes the text at a selector, keeps the first number in it (any currency symbol, separators, a trailing % or a unit around it are dropped) and compares it to within 1e-6. A text with no number at all fails, so an empty selector cannot pass by accident.

A client test does not hand-write its declarations. webc wires > src/wires.h emits the view prototypes, the action prototypes (both the ones bind() names and the ones a view wires with on_click()), and a WIRES_<field> constant per named field — so a test file starts with #include "wires.h" instead of one ACTION(x) line per button, and a new button needs no test-file edit at all. It is generated from the sources, so it cannot drift.

A pointer can be dispatched with a position, which is what makes hover code testable:

c
client_dispatch_at("plot", "pointermove", 150, 10, 600, 200);  // x, y, w, h
EXPECT_SIGNAL(tip_on, 1);
