12. Frontend: DOM and SSR

Reference · docs/reference.md

c
static void view(WBuild *b, void *ctx) {
  el("div") { class_("card");
    el("h1") { text("Hello, %s", name); }
    el("button") { on("click", clicked, ctx); text("+1"); }
  }
}
  • el("tag") { ... } opens an element with a cleanup-linked builder.
  • text(): one argument is a value, two or more are a format.

    text(story->title) prints the title; text("%s/%d", a, b) formats. The count is the whole distinction and it is decided at compile time, because a rule that treats every first argument as a format turns text("100% organic") into 1000rganic and text(row->title) into a read of a nonexistent variadic argument.

  • Attributes, one spelling per concept, each taking a Text, a str or a literal

    (WC_AS_STR, chosen at compile time) and a number where a number belongs: attr("width", 640), attr_i("n", i), class_("card lead"), style("width:50%"), id_("reader"), href(url), src(path), alt(t), title_(t), role(r), rel(r), lang(l), target(t), value_(v), name(n), placeholder(p), type_(t), required(), checked(on), disabled(on). A style is a declaration list, never a format: % in width:50% is a value. Each of the formatted ones has a _fmt companion that formats for you: class_fmt("row row-%d", i), style_fmt("--cols:%d", n), attr_fmt("data-id", "%d", id), post_to_fmt("/flights/%d", id), href_fmt(...), src_fmt(...), id_fmt(...).

  • if in a view is fine. A branch that appears, grows or disappears — including in

    the middle of an element — is a supported render: siblings it did not touch keep their identity (and their DOM node), and the nodes the branch owned are the only ones removed. show(cond) still has its place for the case where a toggle should not cost a node: it flips display:none on an element that stays in the tree, so an open/closed panel keeps its scroll position and its listeners. show() is also the safe way to hide a container that holds a position: fixed child: display:none on an ancestor takes the whole subtree out of hit-testing, while a class_("hidden") that only sets visibility somewhere else may not. When a click goes to an element you cannot see, WebC.why(x, y) in the console names it (§13b).

  • markup(bytes) for bytes that are already HTML (raw() is gone; the name now says what

    the argument is), on(fn, event) for a listener on an element in this view, and bind_str(sig) for a live input bound to a state(Text, …).

  • A live input is one line, in the view, with no matching line in client_main:

    el("input") { attr("name", "reason"); bind_str(reason); } for a state(Text, reason, ""). The two-step form (input_hook(reason) in the view + bind_input(reason) in client_main) still works, and it is order-sensitive — the hook resolves its field when the view runs, so both calls belong where the docs put them. Get it wrong and the field is reported, by name, once rather than doing nothing quietly.

  • Which row was clicked. Inside an action, ev_attr("data-id") (or ev_attr_i64) is the

    nearest value of that attribute at or above the element that fired, and ev_value() is the payload the bridge sent:

c
for_i(i, (*rows)) {
  const Flight *f = at((*rows), i);
  el("tr") { attr("data-id", fmt("%d", f->id)); el("button") { on_click(pick); text("select"); } }
}
action(pick) { i64 id = ev_attr_i64("data-id"); if (id) set(sel, id); }

A keyed list (for_each) still hands its action the item itself; a positional one has no item to hand, and an action that declares one and gets NULL now says so once instead of returning silently.

  • A listener is re-registered every render. An element that a patch reuses keeps its node

    and its data-wc id; it does not keep its listener list. That is not an implementation detail you have to care about — named()/on_click()/bind() just work across renders — but it is why a handler must not close over render-scoped memory: it is called with the context the current render attached.

  • bind_soft(name, event, action) is bind() for a control that is only rendered sometimes

    (a panel behind a branch): it is excluded from the dead-binding report, which keeps its teeth for a name no view ever renders.

  • Reuse: re-rendering the same component patches only nodes whose text or attributes

    changed. A counter that ticks costs one text command.

  • wkeyed_list(n, key_at, item, ctx) reconciles by key and disposes the per-item scope

    when an item leaves; the macro form is for_each(item, vec, KEY) (an index loop is for_i). portal("#modal-root") { ... } puts a subtree under another element, so a dialog escapes its stacking context.

  • for_each is a render loop, not a way to iterate. A key drawn twice in one

    run is a panic naming the key: the key is the model's .pk, and 0 is its unset value — the shape a page of hand-built rows (vec_new + push, no ids) makes. Before the sentence it was a node that was its own sibling and a render that never finished. Each pass opens a keyed item scope on the node that is currently open, and the loop's last statement sweeps every item of that node the pass did not claim. That is what disposes a removed row's scope — and it is also why a for_each that renders nothing (a count, a sum, a find) is not harmless: it runs the sweep on whatever element the view has open. Counting is a plain loop:

c
i32 n = 0; for (i32 i = 0; i < vlen(rows); i++) n += vat(rows, i).lane == lane;

for_each_ptr is the same iteration with no keyed scopes at all.

  • page(View, ctx) renders HTML with data-wc / data-on-* anchors; the bridge adopts

    those nodes on the client without creating any.

12f. Numbers, money and text you build#

A view that shows a number has three small problems and no good place to solve them: the number needs thousands separators, money needs a currency and a sensible zero, and a percentage needs a decimal count that does not jitter frame to frame. Written by hand they come out different in every view — 10038 in one card and $10,038.00 in the next — and the third one silently costs a snprintf into a buffer somebody sized by hand.

c
text(fmt_num(10038));            // "10,038"        (i64; fmt_num_u for u64)
text(fmt_money(10038.4));        // "$10,038"       (< 0.5 prints "$0"; "-$1,235", not "$-1,235")
text(fmt_money_c(1500, "€"));    // "€1,500"
text(fmt_pct(0.0421, 1));        // "4.2%"          (decimals 0..6, clamped)
text(fmt_compact(1_040_000));    // "1.0M"          (k / M / B / T)

All five return Text — a string that lives as long as the current scope, like fmt() — so they nest in class_fmt, attr_fmt, href_fmt and each other, and none of them allocates heap. fmt_pct takes a fraction: 0.0421 is 4.2%, and the one caller that had it backwards is now a compile-time-looking mistake instead of a page that says 0%.

An attribute that is a list of numbers — points, d, stroke-dasharray — is built with a string builder instead of six snprintf calls into a scratch buffer:

c
Buf *b = sb();                                  // a fresh builder, in the render's arena
for (i32 i = 0; i < n; i++) {
  if (i) sb_putc(b, ' ');
  sb_num(b, x_of(i), 1); sb_putc(b, ',');       // stable decimals: no jitter between frames
  sb_num(b, y_of(ys[i]), 1);
}
el("polyline") { class_("curve"); attr("points", sb_str(b)); }

sb() is scoped to the render exactly like fmt(): the buffer is allocated in the render's arena, so a builder per element costs an unreclaimed pointer and nothing else, and calling sb() twice in one element gives you two independent builders (which is what a chart with a band and a line needs). sb_puts, sb_putstr, sb_putc, sb_i64, sb_u64, sb_printf (__attribute__((format(printf, 2, 3))), so a wrong format is a compiler warning), sb_num(b, v, decimals) for a double with fixed decimals, sb_cstr for an API that wants a NUL, sb_str for attr. Outside a render — in a test, or a task — the builder falls back to the current scope's arena and behaves the same way.

12d2. HTML that came from the database: webc/richtext.h#

The framework has three cases for authored bytes, and two would be a floor that leaves the third unwritten: text() / prose() for copy, markup() for bytes you wrote. The third is the one every CMS has — HTML a user wrote and a column stored — and it is the only one that needs a sanitiser.

c
#include <webc/richtext.h>

rich(post->body_html);                              // the default policy: docs, CMS bodies
rich_with(post->body_html, .allow = RICH_TIGHT);     // comments: p, br, a, em, strong, code
rich_with(post->body_html, .no_images = true, .lazy = true);

It parses once and re-emits through el()/attr()/text(), so escaping is not a second implementation: a tag outside the policy is dropped (its text stays), script, style, iframe, svg, math, form, template and friends are dropped with their contents, every attribute value is entity-decoded before it is judged — java&#115;cript: is a javascript: URL and is refused — and href/src/poster accept only http(s), mailto, tel and relative URLs. A data: URI is refused unless .allow_data_images, and then only for a non-SVG image. A <a target="_blank"> and any absolute link get rel="noopener noreferrer" unless the author wrote one. A tag left open is closed at the end of the fragment; a stray closing tag closes nothing; nesting is capped at .max_depth (40).

The same policy answers the questions an article page asks, without a second parser:

c
text("%s", wc_rich_excerpt(post->body_html, 180));   // plain text, cut on a word, with …
text("%d min read", wc_rich_reading_time(post->body_html));   // 200 words a minute, never 0
i32 words; WRichHeading toc[32];
wc_rich_headings_into(post->body_html, toc, 32, &words);      // level, text, stable id
str stored = wc_rich_stamp_ids(body);                // write `id="…"` on every heading, on save

rich() gives a heading an id derived from its own text (getting-started, and -2 for the second one), which is what a table of contents links to; wc_rich_stamp_ids() writes the same ids into the stored fragment so an anchor a reader copied still lands after an edit, and it is idempotent. Neither is Markdown (that is prose()) and neither is a validator: a fragment is the unit, and sanitising on the way out is what makes a stored body safe to render.

12d3. The facts a page states: webc/ld.h#

Every page already says what it is about — the <title>, the og: tags, the prose — and then repeats it for a crawler in a JSON-LD block.

The shape every app arrived at on its own was a fmt() carrying the whole document, a hand-written escaper for each value, and the vocabulary's nesting retyped on every page type. Three things are wrong with it and none of them is the app's — the nesting is knowledge a library should hold, a fmt() cannot omit a key (so a draft claims it was published at "", which is not a date), and the resulting string is not safe in the element it is written into. webc lint names that spelling; this is the door instead:

c
#include <webc/ld.h>

head_ld(ld_blog_posting(.url = abs_url(fmt("/article/%s", p->slug)),
                        .headline = p->title, .description = desc,
                        .image = cover_url, .author = p->author_name,
                        .publisher = brand(site), .published = p->published_at,
                        .modified = p->updated_at, .word_count = p->word_count));

It emits the nesting the vocabulary asks for — author is a Person, publisher is an Organization with a logo ImageObject, image is an ImageObject, mainEntityOfPage is {"@id": …} — and a field you leave null is omitted, never written empty:

json
{"@context":"https://schema.org","@type":"BlogPosting",
 "headline":"Go cutover walkthrough","datePublished":"2026-10-14T20:31:00Z",
 "mainEntityOfPage":{"@id":"https://example.com/article/go"},
 "author":{"@type":"Person","name":"Victor H"},
 "publisher":{"@type":"Organization","name":"VictorTrades"}}
callthe type
ld_article(…) / ld_blog_posting(…) / ld_news_article(…)Article, and the two subtypes
ld_website(…)WebSite, with a SearchAction when you pass .search_url
ld_organization(…), ld_person(…)Organization, Person — logo, sameAs, jobTitle
ld_breadcrumbs(crumbs, n)BreadcrumbList; position counts itself, the last crumb has no item
ld_faq(qa, n)FAQPage; an entry with no answer is skipped
ld_graph(docs, n)one document, many things: the site and the article, linked by @id

Fields are C strings (a row's Text, a fmt(), text_of() for a value already str), URLs are already absolute, and dates are passed through as you hold them — time.h produces ISO-8601, which is what the vocabulary wants. A type that is not here is four jw_* calls in your own function (§5); that is all these are. head_ld() (§7b) is the door, and ASSERT_LD(res, "author.name", …) (§14b) is how a test checks it.

Nothing invariant is left to the caller: position numbering, the @type of every nested object, and the rel on a link are the library's job, because they are the fields a hand-written block gets right once and wrong on the fifth page.

12d4. Authored HTML as a file: partials/#

markup() is for bytes typed next to the code that renders them. A site's head chrome is the other shape of authored HTML — a dozen lines, none of it interpolated, identical on every page — and in a C string every one of those lines is an escape and a line-continuation:

c
// src/server/head.c — before: every line an escape, every attribute a \"
#include <webc/server.h>

static void head_global(void) {
  head_html("<link rel=\"icon\" type=\"image/png\" sizes=\"32x32\" "
            "href=\"/icons/favicon-32x32-dc00edd8.png\">");
  head_html("<meta name=\"theme-color\" media=\"(prefers-color-scheme: dark)\" "
            "content=\"#1b1714\">");
}

The file is the better home for those bytes. partials/<name>.html at the project root is included by name — read once, cached for the process, and verified by webc check:

c
// src/server/head.c — after: the same bytes, as partials/site/head.html
#include <webc/server.h>

static void head_global(void) {
  head_html(partial("site/head"));
}

Three doors take one:

c
// src/server/down.c — chrome into the head, a page from a file, a banner in a view
#include <webc/server.h>

GET("/down") {
  head_html(partial("site/head"));               // the chrome every page carries
  return res_html(200, partial("maintenance"));  // a whole page, still a file
}
// inside any view: markup(partial("cta/banner")) — a partial draws like markup does

What a partial is: authored — markup()'s trust, no sanitiser, because the bytes are yours the moment you commit the file; and static — no interpolation, because a fragment that needs a value is what a view is. What it is not: browser-side. The wasm half ships bytes, not a filesystem, so a fragment both halves render is #embed beside the code that renders it — the partial is for chrome the server owns, which is most of it.

The failures are loud where they can be. A name is a name, not a path — partial("../x") and partial("/etc/passwd") are refused, because the string came from app code. A name with no file is a null str (and one warning, not one per render), head_html() writes nothing, and webc check names the line:

text
error ./src/server/head.c:12
  a partial with no file
  fix: create partials/site/head.html

webc dev watches partials/ with the rest, so editing the file reloads the page the same way editing a view does.

12e. Parts: a view's composition unit#

A part is a plain C function with typed arguments, callable from any view or part — PART declares the shape once, as tuples, and the compiler checks every call site (which a five-int helper never did):

c
// parts.h — the declaration, shared
PART(Avatar, (name, Text), (hue, i64), (online, bool))

// parts.c — the definition is the function PART declared; the body is view code
void Avatar(Text name, i64 hue, bool online) {
  el("span") { class_("avatar"); attr("data-hue", fmt("%lld", (long long)hue));
               text("%s", name); }
}

// any view: Avatar(u->name, u->hue, user_online(c, u->id));

The convention: parts live in src/parts.{h,c} (or a src/parts/ directory), take what they need as arguments — never a context struct whole — and are the unit a shared view composes. webc check sees inside them like any view code.

A part is markup; a part that wants a state of its own is a component, and the call site says so (§11d): comp(Avatar, u->name, u->hue, online) gives the call its own state_own, its own effect_owns and its own teardown. A part that wraps other markup takes a WKids (§11e).

12d. Prose, and markup you authored#

Anything longer than a label is prose, and prose is text, not markup. prose() turns it into paragraphs and the four inline marks, escaping everything else:

c
prose(story->body);          // blank line = <p>; the whole body is escaped first

prose_with(c->body,
           .first = "first-p",          // the first paragraph, styled differently
           .after = pull_quote, .ctx = st,   // called after each paragraph, 1-based
           .link_class = "inline-link"); // class on <a>, if you want one

prose_inline(deck);          // one run, no <p> wrapper: inside your own element
In the textBecomes
a blank linea new <p>
**bold**<strong>
*italic*<em>
`code`<code>
[label](/href)<a href="/href">label</a> — /, #, http(s)://, mailto:, tel:, or a relative path; anything else stays text, so a javascript: URL cannot arrive through copy

The vocabulary is closed on purpose: it is punctuation you can type into a database column and read back in a terminal. It is not Markdown — no headings, lists, images or tables. An unclosed ** or an [ with no ]( is a literal character, because that is what a stray asterisk means. Inside bold, italic and code there is no nesting: the run is escaped text. The render is streaming — plain runs are slices of your string handed straight to the builder — so a 71 KB page does not copy its own copy.

Markup you authored — an icon, a fragment of HTML you wrote by hand — is markup(): the name says what the bytes are, and it is the only way in that skips escaping.

c
el("span") { class_("icon-sun"); attr("aria-hidden", "true"); markup(sun_svg); }

Long copy and markup like that belong in files, not in escaped C string literals. C23 #embed splices the file in at compile time; the , 0 is the trailing NUL:

c
static const char about[] = {
#embed "content/about.txt"
    , 0 };

static const char icon_moon[] = {
#embed "public/assets/icons/moon.svg"
    , 0 };

#embed resolves the path relative to the including file and works for both targets (verified on clang 21 for the host and wasi-sdk clang 23 for wasm), so the same .svg can be the icon in the server-rendered chrome and in the browser half. Copy in a file is copy you can edit as prose: no quoting, no \n\n, no line splicing.

12c. Progressive enhancement#

Every page works with JavaScript off; the module only sharpens it. The two pieces of that sentence are spelled once:

c
// in the chrome, rendered by the server and by the module alike
enhance("reader") {                                  // <div id="reader" data-enhance="reader">
  el("form") { post_to("/theme"); … }                // the no-JavaScript control
}

// a control outside the mount point retires itself once the module is up
el("form") { scripted_hide("themeswitch"); post_to("/theme"); … }

client_main { mount(Reader, "#reader"); }            // replaces the fallback's contents

assets/webc.js sets <html data-wasm="1"> and hides every [data-scripted-hide] element after the module has started, so the fallback and the interactive version are never on the page at the same time.

12g. Where the pointer was#

A pointer event arrives with the fact that matters: where it happened. The bridge sends that with the event, so following the pointer is an action and a signal — not a script, not getBoundingClientRect in a .js file, and not a second source of truth about what the view drew. One app's whole tooltip was 54 lines of JavaScript for this: a document-level pointermove, a closest('g.stratg'), two data- attributes and a fixed div moved with clientX/clientY. All of it is three lines of C now.

c
action(follow) {
  WPoint p = ev_point();                         // the point, inside the element
  set(tip_x, p.cx); set(tip_y, p.cy);            // …or p.x/p.y for the element's own frame
  set(tip_on, 1);
}

view(Tip) {
  if (get(tip_on))
    el("div") { class_("tip"); style_fmt("left:%gpx;top:%gpx", get(tip_x) + 14, get(tip_y) - 12);
                text("Martingale"); }
}

WPoint carries six numbers: x/y inside the element (0,0 at its top-left corner), w/h for the element's own box, and cx/cy on the page (clientX/clientY, which is what a position: fixed element wants). ev_box() is the box alone — the pair a chart needs to turn a pixel into a fraction:

c
action(crosshair) {
  WBox b = ev_box(); WPoint p = ev_point();
  set(at, b.w > 0 ? p.x / b.w : 0);              // where in the plot the pointer is
}

An event with no pointer data — a click fired from the keyboard, a field, a test that did not say where — answers zeroes, so p.w || p.h is the guard and a fraction is never nan. pointermove/pointerdown/pointerleave work for a mouse, a pen and a finger; there is no separate touch vocabulary to write.

Leave events work, and they mean what they say. The bridge listens on the document, and pointerleave/mouseleave/pointerenter/mouseenter/focus/blur do not bubble — so a bind("row", "pointerleave", …) never ran at all, silently, and the hover it was meant to undo stayed on screen. The bridge hears them in the capture phase now, and drops a leave whose relatedTarget is still inside the same named element: the pointer crossing from one child of a group to another fires a leave on the child being left, and without that check the state blinked off and on at every boundary inside the group. The unit is the element carrying the name, so one named("stratg") group is one hover.

A native test says where the pointer was with client_dispatch_at(hook, event, x, y, w, h) (§14b), so hover code is under test like everything else.

The cost is a round trip and a re-render per event (a pointer move arrives at ~60 Hz). That is 2–4 ms for a page-sized view and it is the same render every other event causes; a view that is slower than that is telling you about itself (§11a, and WEBC_RENDER_COST=1 in §13b measures it). If a hover is too expensive, the honest fix is a smaller view behind a named() hook, not a script that positions the element behind the framework's back.

12h. Charts: webc/chart.h#

An app that draws a chart writes the same four things every time: a value-to-pixel map, a tick step a person can read, a downsampler that does not average a spike out of existence, and the points="…" string SVG wants. One app carried 341 lines of it — two scale closures, a "nice number" picker, a bucketed min/max reducers and a %.2f attribute helper — and every one of them is the same code in the next app. So it is a header, opt-in like ui.h:

c
#include <webc/chart.h>

WPlot plot = chart_plot(CW, CH, 64, 24, 20, 34);          // inside a 720×340 viewport
WScale x = chart_x(plot, FLIPS);                          // indices 0..FLIPS
WScale y = chart_y(plot, 0, peak);                        // value 0..peak, y grows up

Buf *pts = sb();
chart_span_points(pts, x, y, eq, FLIPS + 1, 476, 1);      // 476 buckets, 10 001 points in
el("polyline") { class_("curve"); attr("points", sb_str(pts)); attr("fill", "none"); }

f64 ticks[12];
i32 n = chart_ticks(0, peak, 5, ticks, 12);               // 1/2/2.5/5 × 10ⁿ, not 1 387.4
for (i32 i = 0; i < n; i++) grid_line(ticks[i], y_at(ticks[i], plot));

What is in it:

CallWhat it is
chart_lin(lo, hi, p0, p1) / chart_log(...)a scale; p0/p1 may run backwards, which is how a y axis grows upwards
chart_at(s, v) / chart_val(s, px) / chart_frac(s, v)value → pixel, pixel → value (the inverse a crosshair needs), value → 0..1
chart_nice_step(span, want) / chart_ticks(lo, hi, want, out, cap)round steps at 1/2/2.5/5 × 10ⁿ; the tick list is clipped to cap instead of overrunning
chart_decades(lo, hi, out, cap) / chart_log_top(peak)the same for a log axis
chart_plot(w, h, pad_l, pad_r, pad_t, pad_b) / chart_x / chart_ythe plot rectangle and the two scales a chart actually asks for
chart_span_points(b, x, y, ys, n, buckets, decimals)min+max per bucket: a spike survives, a flat stretch costs two points
chart_points(...) / chart_band_points(...)every n-th point; a closed min/max band (a cone, a drawdown envelope)
chart_range(ys, n, &lo, &hi)min and max in one pass

Nothing here decides a colour, a font, a layout or a label format: the labels are the app's, and fmt_num/fmt_pct/fmt_money (§12f) are what they use. It allocates nothing, keeps no state, and is the same source on both targets — so a chart rendered on the server and one patched in the browser agree to the last decimal, which is the property that makes a hydration diff empty.

12b. Routes, resources and forms on the frontend#

c
route("/todos/:id", detail);              // same path syntax as the server router
i64 id = route_param("id");
front_route("-");                          // the current path as a signal

static WRes *res;                          // one per component field
res = res_new(arena, load_todos, ctx, sizeof(Todo));
res_start(res);
if (res_loading(res)) { ... } else if (res_failed(res)) { text("%.*s", (int)res_err_str(res).n, res_err_str(res).p); }

// A resource has four states, and `res_loading()` is "started and not settled" — it is
// false before the first start, so the guard an on-demand fetch wants is expressible:
if (!res_idle(res)) { /* somebody already asked */ }
res_ensure(res);            // start if idle, do nothing otherwise
switch (res_state(res)) { case WRES_IDLE: … case WRES_LOADING: … case WRES_OK: … case WRES_ERR: … }

state(Text, email, "");
WForm f; Signup draft;
form_init(&f, Signup_modelof(), &draft);
el("input") { bind_str(email); }        // two-way: the field writes the signal
draft.email = get(email);
if (!form_submit(&f)) text("%.*s", (int)form_error(&f, "email").n, form_error(&f, "email").p);

A signal that holds text is state(Text, email, "") — Text is what fmt() returns and what text() and set() take, so there is no second string type to convert to: set(email, "ada@example.com"), set(email, fmt("%s@x", user)), and text(get(email)). The str that holds a slice is the parser's type (req->body, query("q")); app code converts at the boundary with WC_AS_STR(slice) and then stays in Text.

query("name") reads the query string first, then an application/x-www-form-urlencoded body — a form posted with JavaScript off puts its values in the body, and the handler that serves it is the same handler the module calls. That is what makes el("form") { post_to("/theme"); el("input") { name("to"); value_("dark"); } } work in both halves without the app building a URL by hand. req_body_field("to") reads the body alone when the distinction matters.

On the server a resource loads in a green task (the page renders loading first); on wasm it runs inline, because there are no threads to wait with. form_submit runs the model's own validators — the same function the request runs, which is the point of one library for both halves.

12b2. Work that takes too long: res_compute#

A resource whose loader is CPU — 21 strategies over 10 000 flips, a Monte Carlo walk, a median of medians — cannot use res_new: wasm has no threads, so the loader would block the page for the whole run. The escape that shipped in one app was "start it in a timer callback and do it all there", which blocks just as hard and, in that app, walked the arena to 2 GiB.

A computed resource is the same four states, with the work split into chunks that yield:

c
static void build_table(WJob *j, void *ctx) {
  State *s = ctx;
  for (i32 i = s->cursor; i < NSTRAT; i++) {
    if (!job_tick(j)) { job_steps(j, i, NSTRAT); s->cursor = i; return; }  // resumed here
    simulate(&s->strats[i]);
    job_steps(j, i + 1, NSTRAT);
  }
  job_done(j);
}

WRes *table = res_compute(nullptr, build_table, &g_state, sizeof(Run));

// in the view
res_ensure_key(table, g_key);                    // start, or restart when the key moved
if (res_loading(table)) { text("simulating %d%%", res_progress(table)); }
else { Run *run = res_data(table); … }
  • job_tick(j) is the whole contract: it answers "you still have time", and a function

    that returns without job_done() is resumed where it left off. The cursor is the app's own loop variable in its own state — there is no closure, no coroutine, and nothing to free.

  • res_ensure_key(r, key) is res_ensure for work that has inputs. The key is the app's

    hash of everything the work depends on (a seed, a slider, the row count); one number, so the framework never guesses at dependencies and never compares a struct it does not know. res_invalidate(r) forces the next one to run again.

  • res_progress(r) is 0..100 from the steps the work reported. Between chunks the view

    re-renders, because a chunk ends in a host callback (§11a) — so the progress bar advances without a signal of its own.

  • The budget is 8 ms per chunk (wc_job_budget_ms), and every chunk gets at least one

    step whatever the budget says: a work function that can never move would otherwise hand control straight back to the pump and spin on timers forever.

  • A native build (a test, an SSR page with no browser to yield to) runs the job to completion

    through the same pump, so a test exercises the chunk loop rather than a special case.

A job is a resource, so res_data, res_ok, res_loading and res_failed all mean what they mean for a fetched one, and a view that shows both kinds needs no second vocabulary.

Client-side routing is three verbs and the same route() table: a selection that should be an address calls push_url() (a new history entry) or replace_url(), the module reads where it is with self_path(), and the back and forward buttons arrive as an action declared with on_nav():

c
static void select(i64 id, bool push) {
  set(sel, id);
  if (push) push_url(id ? WC_AS_STR(link_to(Flight, flight_by(&flights, id))) : str_lit("/"));
}
action(navigate) {          // popstate: the browser moved, the board has not
  WPageMatch m = front_route(self_path());
  ...
}
on_nav(navigate);           // in client_main

The initial paint needs no push: client_main reads self_path() once and sets the selection it names, so a shared link opens on the same leg on both halves.

12i. The standard library: webc/<module>.h#

Everything up to here is the floor: what every WebC app links. The shelf is the other half — the parts of an app that are the same in every app, kept in headers an app includes rather than headers it is built on.

c
#include <webc/table.h>     // the include is the manifest
#include <webc/overlay.h>   // … and the whole cost

A module is header-only, has no hidden state, owns no colour and no wording, and never adds a bridge verb: it may add C, and the browser bridge (assets/webc.js) is the one file an app cannot opt out of, so nothing on the shelf may grow it. webc stdlib lists what exists:

richtext is the expensive one and it is the honest kind: 5.3 KB buys a parser, an allow-list, entity decoding and a URL policy in the browser half, and a page that renders a stored article in wasm needs exactly that. A page that shows HTML the server already sanitised and only renders the shell pays nothing for it.

Each probe is a small page using four or five of the module's verbs, not a call to one helper (which the optimiser folds away and which measures nothing) and not a call to everything (which measures a tutorial). 0 B means the helper folded into code the floor already had. An app that takes none of it pays zero: an unused header is not compiled into anything, and the floor number is the open §10 story, not the shelf's.

Picking. There is no registry, no lockfile and no configuration key. An #include line is the whole mechanism, which means the dependency graph of a WebC app is readable from its first twenty lines and webc stdlib --used can answer "what is this app using" without a build.

webc add <module> is the install: it copies the module's stylesheet into public/stdlib/<module>.css and prints the two lines that are the actual manifest — the #include and the <link> (/public/stdlib/<module>.css: public/ is mounted at /public, and a bare /stdlib/… is a 404 the browser refuses as a stylesheet). The CSS is yours from then on; it is not regenerated, because a module that shipped its own look would be a module that decided what your app looks like. The class names are the contract (badge, field err, aria-sort on a th); the CSS is a starting point.

A total is not a budget. webc api records one name count for the whole surface and one line per module in api.txt, because a sum can stay flat while one module doubles and another is cut. A module that grows fails its own line and the message names it — that is what keeps "pick and choose" true, one module at a time.

table — order without ownership. Rows stay in the app's array; the table keeps a permutation, so a sort is cheap and a row's index survives it (that index is what a delete button posts). The sort is stable, the third click returns to the app's own order, and the sorted column carries aria-sort.

c
static f64 by_bank(const void *r) { return ((const Row *)r)->bank; }
static const WTableKey COLS[] = {{"Team", by_team, nullptr}, {"Bank", by_bank, "right"}};
static i32 g_order[64];

WTable t;
table_init(&t, rows, n, sizeof rows[0], g_order);
table_keys(&t, COLS, WC_ARRLEN(COLS));
table_state(&t, get(sort), (i32)get(page), 20);

table_head(&t, sort_by);          // symbol, not a string: the action has to exist
table_pager(&t, page_flip, "Rows");

overlay — the five details that make a box on top usable: role, aria-modal, a name, focus that moves into it after the batch, and a way out that does not need a mouse. dialog(&O, get(open)) { … } emits the scrim and the panel and nothing when closed; overlay_esc(close_action) is the Escape key. drawer is the same contract with another class, because where the box sits is a stylesheet's business.

The backdrop and the panel are siblings, not parent and child. A scrim that wraps the panel cannot tell a click outside from a click inside — the bridge gives every event in a hook's subtree to that hook — so a <form> inside a dialog submitted nothing and closed the dialog instead. The backdrop carries the close hook; the panel carries an id (the focus target) and no hook at all, which makes it a boundary. examples/board's new-card dialog is the case that found it.

form — the form drawn from the model that validates it. form_fields(&f) walks the model, so the input's kind, its bounds, its label and its error all come from one declaration, and adding a field to a struct adds a field to the form.

c
WForm f;
Signup draft = {0};
form_init(&f, Signup_modelof(), &draft);
el("form") { post_to("/signup");
  form_fields(&f);
  form_errors(&f);
  el("button") { type_("submit"); text("Sign up"); }
}

f.prefix = "edit" gives a second form on the same page its own id space — the thing a hand-written field set gets wrong at the second form. form_field_long(&f, "bio", 6) is the one place a textarea is chosen, because that is a decision about the page, not about the model.

theme — tokens, two editions, and the cascade order that makes the first paint right: the light block, then :root[data-theme=dark], then @media (prefers-color-scheme:dark) with :not([data-theme=light]). theme_head(&T) writes those three declarations into a <style> in the document being rendered; theme_head_html(&T) writes the same thing into the response's <head> from a route (via head_html(), §7b). theme_paint(bool) is what a switch's action calls.

keys — one array of shortcuts, bound by keys_bind(CMDS) and listed by keys_help(CMDS, &BOX, open), so a shortcut cannot be bound and undocumented. keycap() prints meta+k as ⌘K.

motion — enter animation and stagger as two attributes (enter("rise"), stagger(i)) plus one stylesheet, with prefers-reduced-motion switched off for readers who asked. It animates into the page: leaving and reordering need the node held for the duration, which is a DOM decision the bridge owns, and a module may not add a bridge verb. An app that wants that adds it itself.

icons — 45 stroke paths, each its own constant, so only what you draw is linked. A button that is only an icon still needs a name, and the name is not an attribute the caller remembers to add: button_icon(WC_ICON_PLUS, "New card", "new_card") draws the button, sets aria-label and title, and names the hook — an unlabelled icon button is the most common accessibility bug in a hand-written UI. Inside a larger button, icon(d, 0) plus aria_label() is the pair.

dnd — pick a row up and put it down. The module owns the pointer arithmetic and the adjusted drop index, and it does not own your array: dnd_drop() answers where the row lands, adjusted for the row that left, and the app decides what that means.

c
static WDrag g_drag;
dnd_list(&g_drag, WC_ARRLEN(notes));            // role="list", the shared attributes
dnd_row(&g_drag, &notes[i], i, get(from), (i32)get(over));
...
on_drop(move_row);                               // dnd_take(&g_drag, &from, &to)

dnd_keys() prints the keyboard contract (aria-keyshortcuts) and dnd_can() says whether a drop would change anything. It is built on bind + ev_point, so it adds no bridge verb.

live — rooms over SSE: the server half broadcasts a whole document, the client half re-renders it. A burst of writes becomes one frame carrying the newest document, not a queue; a room with no subscribers has no loop and costs nothing; a tab that dies is reclaimed by the coldest-room rule. The client half wraps the bridge's own res_live(), so an app includes one header and pays no new verb.

c
// server: the frame is the model's own encoding, so a subscriber and a tab that just
// loaded the page cannot disagree about what the board is
str doc = live_json(cards);                    // [{"id":1,…}, …]
live_broadcast("board", key, doc);             // in the handler, after the write
GET("/sse/board/:id") { return live_join("board", path("id"), doc, "doc"); }

// client: the same room, through the store that already exists
action(ready) { live_connect("/sse/board/7", "doc", on_doc); }
live_presence(&here);                          // the head count lands in a signal

live_join streams: the seed first (so a tab that opens late is never blank), then a presence frame per head-count change, then one document frame per change, and a comment line every 15 s so a proxy does not close an idle stream.

csv — out: csv_write_row(), csv_header() walk the model, so the columns are the model's own order with the primary key last and .sensitive fields never leaving. In: csv_parse(body) → csv_next(&p, &row) → csv_into(Model, &p, &row, &out), which matches by header name through model_from_form, so a file with its columns reordered still lands correctly. Quoted commas, quotes inside quotes, embedded newlines, \r\n, blank lines and width mismatches are all reported rather than guessed at.

search — a search box that does the one thing that is easy to get wrong: search_where() ANDs the words, ORs the fields, escapes a typed %/_/\, lower-cases both sides, and ranks by the first field you name then by primary key desc. search_hl() highlights in one pass, escaping and marking together, and search_snippet() cuts a window around the first hit with ellipses.

c
static const char *const FIELDS[] = {"title", "body"};
search_where(q, Row_modelof(), FIELDS, WC_ARRLEN(FIELDS), /*limit*/ 20);

i18n — catalogs in arrays, binary-searched, up to four of them (en fallback, then what the request asked for). t("save"), t("greet", "name", name) and tn("files", n) with _one/_few/_many/_other keys; the plural rule is a per-catalog one/slavic/ none, so Polish is not English with different words. i18n_use("de-AT") answers to de, and a missing key renders ??key?? — loud, because a silently blank label is a bug you find in production.

upload — a file arrives and is checked before it is trusted: upload_take(req, "cv", &pol) (the parse happens here — no body(T) first), sniffs the magic bytes (PNG, JPEG, GIF, WebP, PDF, ZIP, WebM, MP4, MP3), checks the policy (image/*), and makes up the name on this side — a random stem plus an extension the mime map chose, never the client's filename. upload_input() is the field; bytes_text() is "1.4 MB".

time — dates, ages and durations with no timezone database: fmt_date(ms, "%Y-%m-%d") over Hinnant's civil algorithms, fmt_date_iso, parse_iso_ms / parse_iso_secs (the unit is in the name; parse_iso still works and is milliseconds — webc check names it), ago(ms) → "3 days ago", dur_ms() in two units. UTC only, and said out loud. (There is no clock() macro: it would shadow libc's, so fmt_date(now(), "%H:%M") is the spelling.)

mail — a real email from one view. mail_view(m, VIEW, ctx) takes the view's name and casts it, so a misspelt view is a compile error and not an empty email; the HTML is turned into a text part (mail_html_to_text), the MIME body is multipart/alternative with both parts base64, and mail_send() writes the message to the outbox first and then tries SMTP (greet, EHLO, STARTTLS, AUTH PLAIN). WEBC_MAIL_OUTBOX means a dev machine with no server still sends something you can read.

jobs — work that outlives the request. WEBC_JOB(send_welcome) declares a job and its work function; the table comes from the model (model_sql_create_table), the claim is one conditional update … where, and a crash is recovered by the lease rather than by a cron sweep. wc_job_worker(n) runs the loop, NAME_later(…, delay) is the one-liner a route calls, and wc_job_failures() is the list you actually want in an admin page.

limits — a rate limit that is one line and a table that cannot grow: 256 fixed slots, four integers per key, oldest evicted. mw_rate_per_ip(60, 60_000) or mw_rate_for("/login", …); the middleware answers 429 with Retry-After. It allocates nothing under attack, because a limiter that allocates under attack fails under attack.

pwa — installable and offline in three calls: pwa_manifest() (JSON, escaped per field), pwa_worker() (navigate → network-first then offline page, assets → cache-first, GET and own-origin only, old caches evicted) and pwa_head(). The cache name is the build id, so a deploy is a new cache and a rollback is an old one.

What the shelf must never contain: a CSS framework, a bundler or a generator, an ORM, a timezone database, image processing, a design system, a second router / state / fetch, or a module that needs a bridge verb. Those are all either opinions an app should hold itself, or the core's job.

12j. Live bindings: a node that updates itself#

§11a's rule — a render follows every action — is the right default because it cannot be wrong. It is the wrong price for a value that changes on every keystroke or pointer move: the framework re-runs the whole view and diffs the whole tree to deliver one text node. On a 5 000-element page that is 3.4 ms of C work to emit the same 12-byte text op a binding emits in 200 ns.

A live binding is that second half. The view says which node carries the value, once:

c
state(i64, count, 0);
state(bool, open, false);
state(Text, label, "ready");

view(Counter) {
  el("span") { text_live("%lld", count); }               // this text node
  el("li")   { class_("row"); class_live("open", open); }
  el("div")  { style("width:1px"); show_live(open); }
  el("i")    { attr_live("data-n", count); }
  el("em")   { text_live("%s", label); }
}

What happens on set(count, 7):

  • The binding re-reads the signal, formats it, and emits **the op the patcher would have

    emitted** — text <id> 7, attr <id> data-n 7. No new bridge verb exists, so the two paths cannot disagree about syntax.

  • A write that does not change the formatted value emits nothing.
  • The text the view drew is updated too, so the next render diffs against what the page

    actually shows: set(x, 1); set(x, 0) cannot leave 1 on screen.

  • Client-only. The server half renders the value and registers nothing, so SSR and

    hydration are byte-for-byte what they were.

What still needs the render. Anything that can add, remove or reorder a node — an if, a for_each, a part, a markup() slot — is the render's job; a binding only ever writes a leaf. So the bridge keeps re-rendering after every event unless the action says otherwise:

c
action_live(follow) {                 // pointermove: signals only, nothing structural
  WPoint p = ev_point();
  set(tip_x, p.cx); set(tip_y, p.cy); set(tip_on, 1);
}
// client_main: bind("tip", "pointermove", follow);

action_live means "this handler writes signals and nothing else"; the flush then sends the bindings' ops and no view body runs. The promise is the action's to keep — it may not change what the view draws. An action that mutates data (a vector, a struct field the markup reads) is a plain action: it costs a render and cannot be wrong. webc check sees the wiring, not the promise, so the rule is written where it is read, in the header.

The numbers (bench in the framework checkout, native -O2, 5 000 elements, one cell changing per event):

C work per eventDOM ops per event
text("%lld", get(tick)), then the render3.4 ms12 B
text_live("%lld", tick)200 ns12 B

webc new --template=web starts with exactly this view — a text_live count and an action_live button — so a new app's first click already costs one op. examples/js is the same thing with more around it: click its bump button and WebC.diagnostics().ops goes up by two (the batch's header and one text line) and a MutationObserver on #root sees one characterData record — where the plain action beside it costs six.

The DOM work was never the problem; the re-render was. What a binding does not do: make a large view mount faster (the first render is still N nodes), or raise the 20 000-op mount budget (§16.8). A very large list still wants pagination or virtualization.

The rules.

  • Types: i32, u32, i64, u64, f32, f64, bool, Text. The type comes from

    the state(…) declaration through _Generic, so nothing else has to say what count is. A state_in/WInst signal has no single node to bind to and is refused; a state_own signal has exactly one, because the binding is declared inside the position that owns it, so it is the supported way to make a row's value live (§11c). An unknown type prints ??live-binding type?? instead of guessing.

  • Ownership: class_live owns one token of class, show_live owns display inside

    style, and both re-read the rest of the attribute from the node on every render — so class_("row") beside class_live("open", open) keeps both. Two bindings on the same attribute of the same node is a bug, and the second silently wins.

  • Lifetime: the binding belongs to the node, so it leaves with the node — a keyed list

    that moves or removes a row takes its bindings along — and a binding the view stops declaring in a run is killed by that run's sweep. wcomp_destroy kills the rest.

  • Identity: re-declaring text_live("%lld", count) on every render re-uses the binding

    (kind + parameter is the identity), which is why a re-render neither duplicates it nor loses it.
