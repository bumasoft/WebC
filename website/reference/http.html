7. HTTP

Reference · docs/reference.md

c
GET("/users/:id") {
  i64 id = path_i64("id");
  return json(200, User, user_find(id));
}

Routes are declared at file scope (a C function cannot be defined inside a function), GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS/ANY, with _MW variants that attach per-route middleware. Matching order is static segment > :param > *wildcard; HEAD falls back to GET; a trailing slash is not a different route; a known path with the wrong method is 405, not 404.

Request helpers: path(name) and query_text(name) are Text — the one string type an app names; path_i64(name), query_i64(name, d), req_query_bool(name, d) are the numbers they stand for. Then query(name) (the raw str, for a value that may be binary), header(name), cookie(name), req->body, req->peer, req->request_id, req->arena.

Responses — one spelling each, and text/html take a C string or a Text alike:

callwhat it sends
json(status, Model, ptr)one row as JSON
json(status, collection) / json_list(status, collection)a collection as JSON; json_list is the spelling the compiler checks
json(status, text)a body you already built
text(status, s) / html(status, s)text/plain / text/html
page(View, ctx), page_with(status, View, ctx)a view inside the shell
res_error(status, code, msg)an error body in the shape the client expects
redirect(url)303 with a Location
res_file, res_download, res_bytes, res_stream, res_sse, res_upgradethe rest
res_cookie, res_header(_str)a header on the response

The last line of a mutation route, either way a browser asks it — a form post gets its redirect back to the page, a JSON call gets the row it changed:

c
return (wc_body_is_form() ? redirect(\"/\") : json(200, Card, k));   // == wc_body_is_form() ? redirect("/") : json(200, Card, k)

Bodies: TRY_BODY(Model, var) parses JSON, TRY_FORM(Model, var) parses application/x-www-form-urlencoded; both validate with the same code the browser would run, and return 422 with {error, message, status} on a failure.

Typed extractors take the model's name and fail the request on bad input (400 invalid_body for malformed JSON, 422 invalid_form for a form that parses but does not validate — the message names the field):

c
POST("/accounts/:id/deposit") {
  Deposit d = body_json(Deposit);     // or body_form(Deposit), body_bytes(), header_i64("x-count")
  return json(202, Deposit, &d);
}

A route can be named with a second argument, and then a URL is built from the pattern instead of spelled again — url_to() fills :params from (name, value) pairs, link_to(Model, row) from the model's own route. A name that is not registered, or a parameter the pattern wants and the call did not pass, panics with the route table rather than producing a 404 a reader finds:

c
GET("/a/:slug", "story") { … }
GET("/s/:slug", "section") { … }

href(url_to("story", "slug", st->slug));      // → /a/the-last-ferry
href(url_to("home"));                          // a route with no parameters
href(link_to(Story, st));                      // WEBC_MODEL_ROUTE(Story, "/a/:slug")

A page's context is filled in by field name when the view names its type with view(Name, CtxType *c), or declare_view(Name, CtxType); in a header — the same view and its context type in one line, which is how a route in another file names it too. Every name is then checked by the compiler — a typo is field designator 'sectoin' does not refer to any field in type 'SectionPage_ctx'; did you mean 'section'? — and the route reads as prose:

c
view(SectionPage, SectionCtx *c) { el("h1") { text(c->section->name); } }

GET("/s/:slug") {
  const Section *sec = must(site_section(site, path("slug")), "no such section");
  return render(SectionPage, .site = site, .section = sec, .list = stories_in(sec));
}

must(ptr, msg…) answers 404 with that sentence when the pointer is null (the whole route, not a paragraph); must_with(status, ptr, msg…) for another status. render_with(status, Name, .field = …) is the same page with a status. page(View, ctx) stays for the one-value case (page(Notes, db_all(Note))).

Route groups are a runtime scope (routes self-register before main, so a lexical block cannot wrap them):

c
group("/api/v1") {
  webc_use(mw_auth_bearer(token));                       // applies to this scope only
  webc_route_add("GET", "/me", me, nullptr, 0);           // prefix becomes /api/v1/me
  group("/admin") { webc_route_add("GET", "/stats", stats, nullptr, 0); }  // prefixes compose
}

An outbound client (dogfooded by webc get):

c
WRespC r;
WErrRes e = http_get(arena, "https://example.com/api", &r);
r.status; r.body; r.content_type; r.location;

// a POST with headers, following at most 5 redirects
WErrRes e2 = http_do_follow(arena, (WClient){ .method = "POST", .url = url, .body = json,
                                               .headers = hdrs, .nheaders = 2 }, 5, &r);

Framing is Connection: close plus chunked decoding; redirects are returned unless you ask for them; TLS needs -DWEBC_TLS=openssl (§16).

Testing without a socket: Response r = webc_test_request("GET", "/users/1");

7b. The page head#

page() splices a view into the <div id="root"> of an HTML file, so the <head> is the file's — but the title, the canonical URL and the social cards are per page. These fill the head of the response being built; the splice happens on the way out and before anything compresses the body (§8b), so it works for page(), for html(), and for a document you assemble by hand — and it reaches a browser that sent Accept-Encoding: gzip, which is all of them:

c
GET("/s/:slug") {
  head_title(fmt("%s — The Meridian", s->name));
  head_meta("description", s->blurb);
  head_prop("og:title", s->name);              // <meta property="og:title" …>
  head_link("canonical", fmt("https://example.com/s/%s", s->slug));
  head_html("<meta name=\"theme-color\" content=\"#fbf8f1\">");  // anything else
  head_html(partial("site/head"));   // a file of chrome (§12d4), rather than nine of those
  head_ld(ld_blog_posting(.headline = s->name, .url = abs_url(path)));  // structured data
  return page(200, Section, &ctx);
}

A <title> the shell already has is replaced where it stands (the file keeps its shape); everything else is appended at the end of <head>. Text is escaped once, on the way in. A response with no </head> — a fragment, JSON — is left alone.

head_ld() is the one exception to "text is escaped on the way in", and it exists because a <script> body is two languages at once. JSON's own escaping does not escape <, so a value containing </script> closes the element and the rest of the document is read as markup — with whatever nonce the framework splices into every <script> on the way out. head_ld() escapes the document for the context (<, >, &, U+2028/U+2029 as \uXXXX) and writes nothing at all for an empty document, because an empty block is invalid rather than neutral. Never build one with head_html(fmt("…")): webc lint names that line.

7b1. A page is a value: head() and WPage#

Five head_* calls in a row are five chances to forget one, and the reader's theme is a sixth thing to remember per route. A page context that begins with WPage gets all of it from render():

c
// app.h — the context is shared, and so is the page
typedef struct SectionCtx {
  WPage page;               // head + environment, first field
  Site site;
  const Section *section;
  const VecStory *list;
} SectionCtx;
declare_view(SectionPage, SectionCtx);

// server.c — the route says what the page is
GET("/s/:slug", "section") {
  return render(SectionPage,
                .page = head(.title = fmt("%s — The Meridian", sec->name),
                             .desc = sec->blurb,
                             .og_title = sec->name,
                             .canonical = fmt("https://example.com/s/%s", sec->slug)),
                .site = site, .section = sec, .list = list);
}

A project may keep its headers in folders — one per concern — and it may keep them apart from the sources too (src/models/people.h, src/views/admin/editor.h). Every .h under src/ is the project's for the engine, whatever folder it is in: WEBC_MODEL, Vec(T) and declare_view are found in all of them, and a #include "app.h" in a nested file resolves because -I src is on every compile line.

head(...) is a compound literal, so every name in it is checked by the compiler. render(), page() and page_with() all call webc_page_begin(&ctx) before the view runs: it fills page.env from the request and records the head, which is spliced into the document before anything compresses it (§8b) — the one-value page(View, ctx) form included, which is what makes the two spellings the same page:

page.headbecomes
title<title>, and og:title unless og_title is given (og_title = "" suppresses it)
desc<meta name="description"> — skipped when empty
og_type, og_image, og_siteog:type, og:image, og:site_name
section_name<meta name="article:section">
canonical, alternate<link rel="canonical">, <link rel="alternate">
page.env (filled, read in the view)
themethe theme cookie when it is light or dark, otherwise ""
darktheme == "dark"
paththis request's path — where a form should send the reader back to
query?q= as text, "" when absent

A theme in env.theme is also written as data-theme on <html>, so the first byte is already the right colour. The types live in <webc/page.h> (shared), because the context is compiled for both targets and a view may read c->page.env.dark; only filling it needs a request. A page with no title logs one line per route, because a document that is wrong in the tab is otherwise silent.

The head_* functions still exist for a response you assemble by hand — webc_page_begin(&page) with a local WPage is the same thing without render().

7b2. <html> and <body>#

A page's document element is per request too: a site that server-renders the reader's theme needs the attribute in the markup before the first byte, or the page flashes the wrong edition. html_attr() and body_attr() splice into <html …> and <body …> on the way out, the same way the head does, so an app never has to assemble a whole document by hand:

c
GET("/") {
  html_attr("data-theme", theme_from_cookie());    // <html lang="en" data-theme="dark">
  body_attr("class", "is-front");
  return page(FrontPage, ctx);
}

7c. Cookies#

res_cookie(res, name, value, attrs) adds Path=/, HttpOnly and SameSite=Lax for you, and Secure on a TLS request. attrs is extra attributes (Max-Age=60, SameSite=Strict, …); an attribute you name yourself replaces the default instead of following it, so nothing appears twice on the wire.

c
res_cookie(res, "theme", "dark", "Max-Age=31536000");
res_cookie(res, "session", token, "HttpOnly; SameSite=Lax");   // exactly once each

7d. A stream that stays correct: the SSE pattern#

res_sse(fn, ctx) hands the response body to fn, which owns a socket for as long as it runs. Three facts shape every correct stream, and none of them is obvious:

c
typedef struct Sub { bool used, live; ChanInt wake; i64 uid, last_v; Response *r; } Sub;
static Sub g_subs[64];
static WMutex g_mu;              // zeroed is an unlocked mutex
static i64 g_vers = 1;

static void bump(void) {         // any mutation ends here
  wmutex_lock(&g_mu);
  g_vers++;
  for (i32 i = 0; i < 64; i++)
    if (g_subs[i].live) { i32 one = 1; wchan_try_send_typed(g_subs[i].wake.c, &one, sizeof one); }
  wmutex_unlock(&g_mu);
}

GET("/api/stream") {
  // …find a free slot, fill it, then:
  return res_sse(stream_run, &g_subs[slot]);
}

static void stream_run(Response *r, void *vp) {
  Sub *s = vp;
  s->r = r; s->live = true; s->last_v = g_vers;
  bump();                        // the newcomer's presence is news; its first frame follows
  WFrame fr;                     // two generations: a frame dies when the next one
  frame_init(&fr, 96 * 1024);    // replaces it (a stream's memory discipline, as a verb)
  for (;;) {
    i64 sig = 0;
    SelCase cs[1] = {SEL_RECV(s->wake.c, &sig)};
    i32 got = select_wait(cs, 1, 15000);        // wake, or heartbeat every 15 s
    if (got == SELECT_CLOSED) break;
    if (got == SELECT_TIMEOUT) { if (!sse_send_text(r, "ping", str_lit("1"))) break; continue; }
    if (g_vers == s->last_v) continue;
    Arena *prev = frame_begin(&fr);             // the fresh generation, made current
    str frame = snapshot_json(prev);
    bool ok = sse_send_text(r, "sync", frame);
    frame_end(&fr, prev);
    if (!ok) break;                             // a dead socket fails on write
    s->last_v = g_vers;
  }
  frame_free(&fr);
  wmutex_lock(&g_mu); s->used = s->live = false; wchan_close(s->wake.c); wmutex_unlock(&g_mu);
  sse_end(r);
  bump();                                       // someone left: presence is news too
}
  • The client half is webc_subscribe("/api/stream", "sync", on_frame); a frame the

    bridge does not know by name (the ping above) is ignored, which is what heartbeats want. Decode frames into a private generation arena and persist() anything that must outlive the frame — the pattern is §13d's WLive, spelled out by hand.

  • Presence is the subscriber list itself; a stale entry leaves when its next write

    fails, which the heartbeat bounds to one interval.

  • A stream parks its task on the channel and on writes; the stall monitor does not

    count it (it is a streamed response, not a stuck handler).

7e. A file, and the part of it the client asked for#

res_file(status, path) is a complete HTTP file response, not a path and a length. It answers the four questions a file has: is this the copy you have (304), all of it or part (200/206), where does it end (416), and may I resume (Accept-Ranges: bytes).

c
GET("/media/:name") { return res_file(200, path("name")); }   // seekable, resumable
GET("/export")      { return res_download(200, "/tmp/report.csv", "q3 report.csv"); }
text
$ curl -D- -H 'Range: bytes=0-1023' /app.wasm
HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 0-1023/96359
Content-Length: 1024

What it decides, and why each one is not optional:

requestanswer
Range: bytes=0-99206, Content-Range: bytes 0-99/907
bytes=800- / bytes=-100206, to the end / the last 100 bytes
bytes=0-99999206, clamped to the last byte — not an error
bytes=907- (a 907-byte file)416 with Content-Range: bytes */907
bytes=0-9,20-29200, the whole file: a server MAY ignore Range, and no browser

asks for multipart/byteranges | | bytes=99-1, bytes=x-y, items=0-9 | 200, the whole file: malformed ranges are ignored | | Range on a POST | ignored: a range is a GET/HEAD idea | | If-None-Match / If-Modified-Since | 304, and the validator wins over the range | | If-Range: <current ETag> | 206; a stale tag or a weak one gets 200, full | | Range + Accept-Encoding: gzip | 206, identity: never compressed (below) |

Three consequences worth knowing:

  • A 206 is never compressed. The offsets in Content-Range are offsets into the

    bytes the client asked about, so a compressed 206 is a deflate stream with a byte count that means nothing; and mw_compress() reads a file into memory to gzip it, which would turn a 1 KB range request into a whole-file read. The middleware skips 206/416, and res_file() resolves the range before the middleware sees the response.

  • If-Range is what makes a resumed download safe. A client that lost its connection

    re-asks with the tag it has; if the file changed underneath it the answer is 200 and the whole new file, because splicing two versions is worse than a re-download.

  • res_download() escapes the name twice. An ASCII fallback ("; rm -rf ~ becomes

    attachment; filename="_; rm -rf ~_") and filename*=UTF-8''… for names the fallback cannot spell — a quote or a semicolon reaching a header is response splitting.

This is also what webc serve and mw_static() serve, because both go through the same res_file(): a deployment with no nginx in front of it still has a media server.
